# 05 — CLI, MCP, configuração e experiência de agente

## 1. Convenções do CLI

Executável `testmaster`. Comandos abaixo são contratos futuros, não instalação já disponível. Flags globais: `--profile`, `--project`, `--endpoint`, `--output json|text`, `--request-timeout`, `--no-color`, `--verbose`, `--dry-run`. Unidade dos timeouts CLI = segundos, wire = milissegundos; converter uma vez com range validation. Paths resolvidos pelo cwd explícito, não HOME/repo remoto inferido.

`--output json`: exatamente um documento JSON UTF-8 no stdout; logs/ticker/detalhes humanos stderr. Download binário/código usa `--out`, ou stdout somente em modo text explicitamente escolhido. `--output jsonl` não é alias implícito: streaming somente `events --format ndjson`. Secrets, cookie/token, signed URL com credencial e payload sensível não aparecem no debug.

`--dry-run` faz parsing/validação local e descreve ações previstas em `{dryRun:true,validated,operations:[],unresolvedPreconditions:[]}`; não autentica, não abre browser, não inicia LLM, não altera disco. Pode ler arquivos locais explicitamente passados. Não emite falso verdict. `validated:true` só depois de o comando validar de fato a entrada (o `prepare` do comando, ou o lint de `--plan`/`--dir`); `operations` lista o que o comando faria (por exemplo `requirement approve`: `requirement.approve` com a versão resultante; `plan generate`: `proposals.generate` com tipo, requisitos e modelo) e `unresolvedPreconditions` o que só a execução real pode checar (versão, snapshot, e que o provedor do modelo seja permitido por `allowedModelProviders` em `policy.json`). Um comando sem validação local responde `validated:false` com a precondição `no local dry-run validation`, nunca `validated:true`; entrada inválida falha (exit 5) e o envelope traz `data` com `validated:false` ao lado de `error`. Um comando que declara a própria opção `--dry-run` (`worker reconcile`) a implementa ele mesmo. `--example` é tratado antes da validação de opções obrigatórias do comando e imprime `example:true` com o contrato de entrada do comando (uso, argumentos, opções) e, para comandos que leem um arquivo (`auth-profile create --file`, `test create --plan`, ...), um arquivo de exemplo completo e válido em `fixture.input.content`; é separado de dry-run.

`--help` lists an option the command cannot run without as `(required)` (for example `auth-profile test-login <id> --environment <id> (required)`), so a missing one is known before the call; the refusal at call time is `INVALID_ARGUMENT` and names the option.

| Plan | `plan trial <batch-id> [--env ID-OR-NAME] [--only ID,...] [--timeout SECONDS]` | Replays the plans of the batch's `proposed`, valid, executable proposals (all of them, or `--only`) against the environment (default: the project's default environment) before review, exactly like a replay run (sandbox, egress, secrets, auth profiles, evidence; healing off, origin `trial`), with no model call; batch and proposal versions do not change. Each plan runs from a hidden trial test (`extensions['testmaster:trial'] {batchId, proposalId}`, archived, no active revision, one per proposal, one revision per plan content) that never appears in test listings, selection, suites, coverage or the feature map and that normal run admission refuses (`PRECONDITION_FAILED`, "A plan trial test is not runnable"); trial runs stay readable (`run get/steps`, analysis). The receipt is `PlanTrialReceipt {batchId, batchVersion, environmentId, trials: [{proposalId, proposalVersion, planName, tried, reason?, runId?, outcome?, gate?, cleanupOutcome?, reasonCode?, failedSteps: [{stepId, status, reasonCode?, message?, expected, observed}]}]}`; a proposal that is not `proposed`, invalid, an intent plan, depends on another test's captures or is refused at admission is `tried: false` with its reason. `--all` e IDs exclusivos; `--filter`, `--tag`, `--priority`, `--status` combinam AND, valores múltiplos de mesmo filtro OR. Seleção não vazia default. `--max-concurrency` limita despacho, não apenas polls. `--env` determina settings; `--target-url` altera destino sem mutar env e não encaminha auth cross-origin sem aprovação. `--local PORT` é atalho para local-loopback profile do TestMaster, **não significa cloud tunnel**. Execução remota local exige `--executor remote --tunnel ID`. Local backend também suportado pela bridge; não copiar limitação TestSprite de URL hardcoded.

Paging and outputs: `source list`, `env list`, `plan list`, `test list`, `requirement list`, `feature list` and `run list` page only when `--limit N` or `--cursor C` is given (the cursor is signed, bound to the list, its filter and the principal, and carries the page size), printing `{total, returned, items, nextCursor}` (`nextCursor` null on the last page); without either they print the whole array as before. Against `--endpoint`, list commands follow every server page (100 a page), restart the walk once from the first page when a cursor expires, and print the whole array; remote `test list` forwards one `--tag` and one `--priority`, refuses an empty `--tag` or `--priority` with `INVALID_ARGUMENT`, and refuses `--status`, a repeated `--tag` or `--priority`, `--limit` and `--cursor` with `CAPABILITY_UNAVAILABLE`; remote `run list` forwards `--test`, `--batch`, `--status`, `--since` and `--project` and refuses `--limit` and `--cursor` the same way. `plan get <batch>` pages the proposals with `--limit`/`--cursor` (`{batch, total, returned, proposals, nextCursor}`) or writes the whole `{batch, proposals}` with `--out PATH` (receipt `{path, bytes, sha256}`); `test export <id> --out DIR` prints only `files: [{path, bytes, sha256}]`.

Examples: every command that reads a JSON document (`--file`, `--plan`, `--selection-file`, `--document`, `--mutation-actions`) answers `--example` with a valid sample per mode, checked against its contract (`input.contract`, `input.variant`): `auth-profile create --example --kind form|form-browser|basic|bearer|api-key|cookie|oauth|oidc|manual`, `suite create|update|add --example --kind fixed|dynamic`, `schedule create|update --example --kind cron|interval|revisions`, `test create|lint|revision create` and `plan edit --example --type frontend|backend|cli`. A variant flag outside `--example` is refused. A unit test fails the build when such an option has no example.

Files and audit: every user-supplied input or output path of the CLI goes through `ConfinedRoot`: a symbolic link on the path, a non-directory parent, a directory where a file is expected or a hard-linked file is `FORBIDDEN` (exit 3), and an output file is created exclusively, never replaced. `--dry-run` (including `mcp serve`) authenticates nothing, calls no model and leaves the database and the file tree unchanged. Every local command that opens a workspace appends one audit row (`cli.command.completed`, `cli.command.denied` for `INVALID_ARGUMENT`/`UNAUTHENTICATED`/`FORBIDDEN`/`POLICY_DENIED`, `cli.command.failed` otherwise) with the actor, the command path, the envelope's `requestId` and a hash of command and outcome, never the arguments; an unwritable row is reported as `details.auditRecorded: false` or a warning.

Error bodies: the CLI, REST and MCP build an error body with the same function (`errorBody`): `code`, `message`, a boolean `retryable` (true only for unconditionally retryable codes), `details` (with `issues` merged) and `nextActions`; `validation/journeys/surface-parity.docker.test.ts` compares the whole body across the built CLI, REST, stdio MCP and HTTP MCP per operation, plus the HTTP status and the exit code against the registry.

## 3. Exit codes

| Code | Significado |
|---|---|
| 0 | comando concluído; com `--wait`, gate passou. Sem wait, só receipt aceito. Um gate que não passou nunca sai com 0, qualquer que seja o `reasonCode` (um Run passed com gate failed sai com 1) |
| 1 | verdict/gate não aprovado, flake encontrado, cleanup obrigatório falhou |
| 3 | auth/authorization |
| 4 | resource not found |
| 5 | input inválido, seleção vazia, payload limite |
| 6 | conflito/precondição/revisão |
| 7 | wait deadline, run ainda pode existir; nunca alias de unsupported |
| 8 | capability indisponível |
| 9 | policy refusal to act (`POLICY_DENIED`), `doctor` FAIL (sandbox unavailable) |
| 10 | transport/platform unavailable |
| 11 | rate-limit transitório |
| 12 | quota esgotada |
| 14 | client/schema major incompatível |
| 15 | run completed `blocked` (`security_precondition_failed`, `approval_required`, `egress_denied`, or `blocked` without a mapped reason); the run exists and has evidence: read `run get`/`run analyze` for the cause |
| 129/130/143 | SIGHUP/SIGINT/SIGTERM após receipt parcial/cleanup aplicável |

Sem code 2 “não implementado”: comando não disponível não finge implementação. Precedência batch: auth/policy/version → validation/conflict/notfound → quota → transport/rate → wait timeout → blocked run (15) → nonpass → success. JSON por membro mantém causa original; nunca reduzir todos erros a timeout. O exit não é suficiente para saber se algum teste foi aprovado: ler gate e contagens.

## 4. Cancelar, destacar e retomar

- Job em supervisor persistente/servidor: Ctrl-C durante wait destaca, salvo `--cancel-on-interrupt`. Timeout de espera não cancela por padrão. O limite de espera (`--timeout`, `--request-timeout`) nunca se aplica a um run que o próprio processo executa: a espera continua, só uma interrupção o cancela, e o limite informado gera um aviso.
- Processo local efêmero dono da sandbox: interrupção cancela o job, espera cleanup limitado e termina filhos. Documento/receipt registra ownership antes de executar. Não prometer detach se não há processo durável.
- Túnel de terceiro: interromper borrower não fecha tunnel; owner interrompido revoga binding. Jobs sem transporte ficam cancelled/inconclusive segundo confirmação de efeitos, nunca continuam invisivelmente verdes.
- Cancel solicitado ≠ cancel concluído. Receipt retorna `requested`, `already_terminal` ou `rejected`; CLI lê resultado final até deadline de cancelamento.

## 5. Arquivos e precedência

```text
~/.config/testmaster/profiles.json   # Endpoint and profile metadata
~/.local/share/testmaster/          # Local state and encrypted secrets
<repo>/testmaster.config.json       # Versionable project configuration
<repo>/testmaster_tests/            # Approved plans and exported code
<repo>/.testmaster/                 # Runs, cache, local database; ignored
```

XDG no Linux, application data dirs apropriados nos demais OS. Diretórios privados 0700 e secrets 0600; Windows ACL equivalente. Precedência flag → `TESTMASTER_*` → config do projeto → perfil → default. Config cannot override server security policy; effectiveConfig expõe origens e redacts refs secret. `TESTMASTER_API_KEY`, `TESTMASTER_MODEL_API_KEY`, `TESTMASTER_ENDPOINT`, `TESTMASTER_PROFILE`, `TESTMASTER_PROJECT_ID`, `TESTMASTER_DATA_DIR`, `TESTMASTER_OFFLINE`, `TESTMASTER_NO_TELEMETRY`. Offline impede registry/update/remote LLM/upload, mas **target autorizado local continua acessível**; target remoto requer desativar offline explicitamente.

A Run's recorded `effectiveConfig.config.environment` is the pinned EnvironmentRevision it executed against (`baseUrl` is the origin it targeted, each `environment.*` origin is `environmentRevision`), never the project file's `environment` section. That section and `TESTMASTER_BASE_URL`, `TESTMASTER_NETWORK_PROFILE`, `TESTMASTER_LOCALE` and `TESTMASTER_TIMEZONE` only seed the first Environment at `init` (plus the model request locale and the `doctor` timezone check), so `testmaster_update_environment` leaves the file untouched and no Run states the file's values as effective.

```json
{
  "schemaVersion": "1.0.0",
  "project": {"name": "Example Shop"},
  "execution": {"executor": "docker", "mode": "replay", "concurrency": 2, "executionTimeoutMs": 600000, "attemptTimeoutMs": 300000, "stepTimeoutMs": 30000, "maxAttempts": 1},

```

Este exemplo restringe o prazo e tentativas, em vez de redefinir os defaults de [operação](08-operations.md). CLI `test run` default replay; config healing propose permite somente diagnóstico após replay, nunca invoca LLM se nenhum provider autorizado. Trace/vídeo bruto é opt-in explícito autorizado como `restrictedRaw`, não fallback da coleta sanitizada. `CI=true` força heal off por default e reprova retry-pass/flaky; override exige policy file aprovada, sem poder ocultar assertion failed. Repo de terceiro não pode habilitar provider/upload/unsafe-local por config sozinho.

## 6. MCP

Usar SDK oficial e versão do protocolo **negociada**, pinada no release testado. Baseline 2025-06-18 observada na pesquisa; não alegar latest sem verificar 2026-07-28 e SDK na implementação. Root fora dos roots aprovados ou symlink escape recusado. Secrets não via tool arg livre: aceitar secretRef ou input seguro fora do transcript. Sampling do cliente só quando o cliente anuncia a capability e a política do operador a permite; BYOK gateway é modo separado e explicitado.

Tool metadata: every input property has a description; `budget`, `limits` and `mode` are typed, and `generate_tests` takes `proposalIds` or `revisionIds` (at least one, enforced at run time); no advertised input schema uses a top-level `anyOf`/`oneOf`/`allOf`. No tool advertises an `outputSchema` (the protocol makes it optional, and three of them would inline the whole `ExecutablePlan`): the rules page `testmaster://tools/{name}` names the result contract under `## Result`, `testmaster://schemas/{name}` serves it, and the server validates every `structuredContent` against it before answering. No advertised schema inlines `ExecutablePlan` or exceeds 12 KB, and a test locks the size of the whole `tools/list` payload. The tools with a large nested input (`save_auth_profile`, `save_suite`, `review_requirements`, `update_environment`, `explore`, `run_tests`) advertise their top-level arguments only (type, description, allowed values) with a `$comment` naming `testmaster://tools/{name}` and `testmaster://schemas/Mcp_{name}`, because several clients forward every advertised input schema to the model on every turn; every call is still validated against the full contract. Argument errors read `Invalid arguments for <tool>` with each issue once, and an enumeration names its allowed values. Annotation classes: reads (`capabilities`, `validate_document`, `get_run`, `get_analysis`, `review_healing`, `get_evidence`, `open_report`, `compare_runs`) are read-only and idempotent; additive tools (`bootstrap`, `analyze_code`, `normalize_requirements`, `explore`, `generate_plan`, `generate_tests`, `propose_healing`, `analyze_run`, `save_test`, `approve_execution`) create records without altering existing ones and are not destructive; `run_tests`, `cancel_run`, `approve_healing`, `reject_healing`, `review_plan`, `edit_plan`, `promote_revision`, `archive_test`, `archive_source`, `save_suite` and `test_auth_login` are destructive. The hints never replace the scope check.

Sources in the planning flow (MCP, CLI `requirement normalize`/`plan generate` and REST alike): `testmaster_normalize_requirements` takes the revisions that should become requirements, and a PRD section (heading, statement, acceptance criteria) normalizes to one requirement, its criteria being the list items under it. An API specification (`source add --role api-spec`) does not have to be normalized: `testmaster_generate_plan` offers the model the operations and response-schema pointers of every active specification source of the project, so a `jsonSchema` assertion can cite it while the requirements stay scoped to the PRD. No tool input selects the specifications; archiving a source (`source archive`, MCP `testmaster_archive_source`) removes it from the offer and from operation coverage.

Normalization is single-flight per project across processes (the MCP server and the CLI share one database): a request for a project that is already being normalized waits for it instead of starting a second paid call, and only the caller's cancellation ends the wait (a model call has no deadline). When the normalization it waited for committed a snapshot for the same source revisions and the same `provider`/`model` on the version the waiter saw, the waiter returns that snapshot (same `version` and `sourceSnapshotId`) without a model call; otherwise it normalizes on the new version, so two normalizations never fail each other. A holder whose process died frees the project when its lease expires. `REVISION_CONFLICT` therefore means that something other than a normalization (a requirement edit, approval or rejection) changed the requirements during the call: its message names the current version, says the new requirements were not stored and points to `testmaster://requirements/{projectId}` (CLI: `requirement list`) before normalizing again.

`mcp serve` over stdio finishes in-flight calls and exits 0 when the client closes stdin. A missing or unreadable token file is `UNAUTHENTICATED` and names the file and `testmaster token issue --token-file <file>`; a root refusal (`FORBIDDEN`) lists `approvedRoots` (or `clientRoots`) in its details and on stderr.

## 7. Jornadas propostas

```bash
# Local deterministic path; the application must already be running.
testmaster init --mode local
testmaster doctor
testmaster test lint --plan testmaster_tests/login.plan.json
testmaster test create --plan testmaster_tests/login.plan.json --output json
testmaster test run "$TEST_ID" --env local --wait --output json
testmaster artifact get "$RUN_ID" --out .testmaster/failure
# Apply application fix outside the runner, then replay the same test revision.

```

IA: `source add` → `discover` → `plan generate` → `plan get` → `plan accept --only` → `test run --mode agent` com política e modelo → `test revision promote` após revisão. CI usa a revisão aprovada e `--mode replay --heal off`, nunca `latest` não pinado para release.
