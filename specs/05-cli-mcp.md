# 05 — CLI, MCP, configuração e experiência de agente

## 1. Convenções do CLI

Executável `testmaster`. Comandos abaixo são contratos futuros, não instalação já disponível. Flags globais: `--profile`, `--project`, `--endpoint`, `--output json|text`, `--request-timeout`, `--no-color`, `--verbose`, `--dry-run`. Unidade dos timeouts CLI = segundos, wire = milissegundos; converter uma vez com range validation. Paths resolvidos pelo cwd explícito, não HOME/repo remoto inferido.

`--output json`: exatamente um documento JSON UTF-8 no stdout; logs/ticker/detalhes humanos stderr. Download binário/código usa `--out`, ou stdout somente em modo text explicitamente escolhido. `--output jsonl` não é alias implícito: streaming somente `events --format ndjson`. Secrets, cookie/token, signed URL com credencial e payload sensível não aparecem no debug.

`--dry-run` faz parsing/validação local e descreve ações previstas em `{dryRun:true,validated,operations:[],unresolvedPreconditions:[]}`; não autentica, não abre browser, não inicia LLM, não altera disco. Pode ler arquivos locais explicitamente passados. Não emite falso verdict. `validated:true` só depois de o comando validar de fato a entrada (o `prepare` do comando, ou o lint de `--plan`/`--dir`); `operations` lista o que o comando faria (por exemplo `requirement approve`: `requirement.approve` com a versão resultante; `plan generate`: `proposals.generate` com tipo, requisitos e modelo) e `unresolvedPreconditions` o que só a execução real pode checar (versão, snapshot, consentimento). Um comando sem validação local responde `validated:false` com a precondição `no local dry-run validation`, nunca `validated:true`; entrada inválida falha (exit 5) e o envelope traz `data` com `validated:false` ao lado de `error`. Um comando que declara a própria opção `--dry-run` (`worker reconcile`) a implementa ele mesmo. `--example` é tratado antes da validação de opções obrigatórias do comando e imprime `example:true` com o contrato de entrada do comando (uso, argumentos, opções) e, para comandos que leem um arquivo (`auth-profile create --file`, `test create --plan`, ...), um arquivo de exemplo completo e válido em `fixture.input.content`; é separado de dry-run.

`--help` lists an option the command cannot run without as `(required)` (for example `auth-profile test-login <id> --environment <id> (required)`), so a missing one is known before the call; the refusal at call time is `INVALID_ARGUMENT` and names the option.

Execução remota local exige `--executor remote --tunnel ID`. Local backend também suportado pela bridge; não copiar limitação TestSprite de URL hardcoded.

## 3. Exit codes

| Code | Significado |
|---|---|
| 0 | comando concluído; com `--wait`, gate passou. Sem wait, só receipt aceito. Um gate que não passou nunca sai com 0, qualquer que seja o `reasonCode` (um Run passed com gate failed sai com 1) |
| 1 | verdict/gate não aprovado, flake encontrado, cleanup obrigatório falhou |
| 3 | auth/authorization |
| 4 | resource not found |
| 5 | input inválido, seleção vazia, payload limite |
| 6 | conflito/precondição/revisão |
| 7 | wait deadline, run ainda pode existir; nunca alias de unsupported |
| 8 | capability indisponível |
| 9 | policy refusal to act (`POLICY_DENIED`), `doctor` FAIL (sandbox unavailable) |
| 10 | transport/platform unavailable |
| 11 | rate-limit transitório |
| 12 | budget/quota esgotado |
| 14 | client/schema major incompatível |
| 15 | run completed `blocked` (`security_precondition_failed`, `approval_required`, `egress_denied`, or `blocked` without a mapped reason); the run exists and has evidence: read `run get`/`run analyze` for the cause |
| 129/130/143 | SIGHUP/SIGINT/SIGTERM após receipt parcial/cleanup aplicável |

Sem code 2 “não implementado”: comando não disponível não finge implementação. Precedência batch: auth/policy/version → validation/conflict/notfound → budget → transport/rate → wait timeout → blocked run (15) → nonpass → success. JSON por membro mantém causa original; nunca reduzir todos erros a timeout. O exit não é suficiente para saber se algum teste foi aprovado: ler gate e contagens.

## 4. Cancelar, destacar e retomar

- Job em supervisor persistente/servidor: Ctrl-C durante wait destaca, salvo `--cancel-on-interrupt`. Timeout de espera não cancela por padrão.
- Processo local efêmero dono da sandbox: interrupção cancela o job, espera cleanup limitado e termina filhos. Documento/receipt registra ownership antes de executar. Não prometer detach se não há processo durável.
- Túnel de terceiro: interromper borrower não fecha tunnel; owner interrompido revoga binding. Jobs sem transporte ficam cancelled/inconclusive segundo confirmação de efeitos, nunca continuam invisivelmente verdes.
- Cancel solicitado ≠ cancel concluído. Receipt retorna `requested`, `already_terminal` ou `rejected`; CLI lê resultado final até deadline de cancelamento.

## 5. Arquivos e precedência

```text
~/.config/testmaster/profiles.json   # Endpoint and profile metadata
~/.local/share/testmaster/          # Local state and encrypted secrets
<repo>/testmaster.config.json       # Versionable project configuration
<repo>/testmaster_tests/            # Approved plans and exported code
<repo>/.testmaster/                 # Runs, cache, local database; ignored
```

XDG no Linux, application data dirs apropriados nos demais OS. Diretórios privados 0700 e secrets 0600; Windows ACL equivalente. Precedência flag → `TESTMASTER_*` → config do projeto → perfil → default. Config cannot override server security policy; effectiveConfig expõe origens e redacts refs secret. `TESTMASTER_API_KEY`, `TESTMASTER_MODEL_API_KEY`, `TESTMASTER_ENDPOINT`, `TESTMASTER_PROFILE`, `TESTMASTER_PROJECT_ID`, `TESTMASTER_DATA_DIR`, `TESTMASTER_OFFLINE`, `TESTMASTER_NO_TELEMETRY`. Offline impede registry/update/remote LLM/upload, mas **target autorizado local continua acessível**; target remoto requer desativar offline explicitamente.

A Run's recorded `effectiveConfig.config.environment` is the pinned EnvironmentRevision it executed against (`baseUrl` is the origin it targeted, each `environment.*` origin is `environmentRevision`), never the project file's `environment` section. That section and `TESTMASTER_BASE_URL`, `TESTMASTER_NETWORK_PROFILE`, `TESTMASTER_LOCALE` and `TESTMASTER_TIMEZONE` only seed the first Environment at `init` (plus the model request locale and the `doctor` timezone check), so `testmaster_update_environment` leaves the file untouched and no Run states the file's values as effective.

```json
{
  "schemaVersion": "1.0.0",
  "project": {"name": "Example Shop"},
  "execution": {"executor": "docker", "mode": "replay", "concurrency": 2, "executionTimeoutMs": 600000, "attemptTimeoutMs": 300000, "stepTimeoutMs": 30000, "maxAttempts": 1},
  "environment": {"baseUrl": "http://127.0.0.1:3000", "networkProfile": "local-loopback", "locale": "pt-BR", "timezone": "America/Sao_Paulo"},
  "browser": {"name": "chromium", "viewport": {"width": 1280, "height": 720}, "testIdAttributes": ["data-testid"]},
  "healing": {"mode": "propose"},
  "artifacts": {"trace": "off", "video": "off", "retentionDays": 30},
  "telemetry": {"enabled": false}
}
```

Este exemplo restringe o prazo e tentativas, em vez de redefinir os defaults de [operação](08-operations.md). CLI `test run` default replay; config healing propose permite somente diagnóstico após replay, nunca invoca LLM se nenhum provider autorizado. Trace/vídeo bruto é opt-in explícito autorizado como `restrictedRaw`, não fallback da coleta sanitizada. `CI=true` força heal off por default e reprova retry-pass/flaky; override exige policy file aprovada, sem poder ocultar assertion failed. Repo de terceiro não pode habilitar provider/upload/unsafe-local por config sozinho.

## 6. MCP

Usar SDK oficial e versão do protocolo **negociada**, pinada no release testado. Baseline 2025-06-18 observada na pesquisa; não alegar latest sem verificar 2026-07-28 e SDK na implementação. Tools `inputSchema`/`outputSchema`, `structuredContent`, `isError` conforme protocolo suportado. Annotations readOnly/destructive/idempotent são sugestões, nunca fronteira de segurança.

| Tool | Entrada | Saída / efeito |
|---|---|---|
| `testmaster_capabilities` | nenhum | capabilities e limites |
| `testmaster_bootstrap` | projectRoot, target (http/https URL without credentials), scope (`codebase`/`diff`), mode (`replay`/`agent`) | Idempotent per approved root: returns the project bound to the root (its `testmaster.config.json` `project.id` or a stored mapping), else creates one; a project that owns the slug but is bound to no root is `PRECONDITION_FAILED` with `details.projectId`. Resources: `testmaster://projects/{id}`, `/runs/{id}/result`, `/runs/{id}/manifest`, `/runs/{id}/report{?format,cursor}`, `/batches/{id}/report{?format,cursor}`, `/runs/{id}/artifacts/{+path}{?attemptId,offset}` (RFC 6570 reserved expansion: `path` is the artifact's `relativePath` written with plain slashes, `artifacts/browser/steps/x.json`, or as one segment with each slash encoded, `artifacts/browser%2Fsteps%2Fx.json`; both read the same bytes, each segment is decoded and the segments are joined with `/`, and the lookup stays an exact match on the manifest's `relativePath`, so a `..` or empty segment finds nothing and the read is `NOT_FOUND`), `/revisions/{id}/plan`, `/requirements/{projectId}` (a requirement id returns one requirement; every requirement carries `status`, one of `pending`, `approved`, `rejected` or `superseded`, derived from its approval, its rejection and the decided conflicts and never stored), `/projects/{projectId}/features{?match,cursor}` (the project's current features, `{id, stableKey}`, ordered by key and paged 100 at a time; `match` keeps keys containing the text, case-insensitively; `next` is the following page. Features are a cumulative registry that is never deleted from, because requirements, explorations and feature maps cite their ids; the listing hides the ones an earlier analysis found and the current one does not. The current analysis is the newest completed codebase-scope discovery plus the completed diff-scope discoveries after it; a codebase discovery that could not read Python (`unreachable`) adds its features without retiring older ones. A feature no discovery ever found (observed by exploration) is always listed, and so is every feature of a project with no completed discovery. A hidden feature is still readable by id and accepted by `testmaster_explore`). Read-only resources that close the gaps an agent otherwise fills with the CLI, all paged with a signed cursor bound to the list (`total` counts every item, `returned` the items of this page, `next` is the following page, `null` on the last; a cursor reused with another filter is `-32602`): `/runs/{id}/steps{?attemptId,cursor}` (`run steps`; 50 per page), `/revisions/{id}` (`test revision get`, with `resources.plan` and `resources.code`), `/revisions/{id}/code{?format}` (the files of the revision's code, as `test export` and `GET /revisions/{id}/code` read it: `path`, `sizeBytes`, `sha256`, the `resource` of each file and its text as `content`, plus the export `metadata`; the text of the files together is inline up to `inlineLimitBytes` (65536, one resource page, so a listing never costs more than reading one large file); a file that no longer fits has `content: null` and is read at its `resource`; `format` is `playwright` or `pytest`, the default follows the revision's runner, imported code keeps its own and a plan revision exports to either), `/revisions/{id}/code/{+path}{?format,offset}` (one file as `text/plain` pages; `path` is written with plain slashes or with each slash encoded, like an artifact path, and the lookup is an exact match on the revision's file names), `/tests/{id}`, `/tests/{id}/revisions{?cursor}` (revisions in ordinal order without plans, `active` marks the one runs use), `/projects/{projectId}/tests{?tag,priority,status,cursor}` (`test list`; 100 per page; `status` is `active` or `archived`), `/projects/{projectId}/sources{?cursor}` and `/sources/{id}` (`source list`/`get`; the source with its active revision without chunks, `chunkCount` and `diagnostics`), `/projects/{projectId}/environments{?cursor}` (`env list`; 100 per page; each environment, archived ones included, with `default` when it is the project's default and `activeRevision`, the view `env revisions` prints: target and additional origins, network profile, auth profile references, locale, timezone, production; revision variables, which may hold captured values, stay out; `version` is the `expectedVersion` of `testmaster_update_environment`), `/projects/{projectId}/plan-batches{?cursor}` and `/plan-batches/{id}{?cursor}` (`plan list`/`get`; a batch with its proposals, 10 per page; `batch.version` is the `expectedVersion` of `testmaster_review_plan` and each proposal's own `version` is that of `testmaster_edit_plan`). `/runs/{id}/report` and `/batches/{id}/report` take `format` json (default), junit, markdown or html and serve the document with its media type (`application/xml` for JUnit); `/batches/{id}/report` is the aggregate report of a `run_tests` batch or suite run (`batchId` of the receipt, `bat_…`; a run id is `-32002` there) and its `_meta` carries `testmaster:batch` (`batchId`, `requested`, `memberRuns`) where a run report carries `testmaster:result`; Allure is a directory of files and stays on the CLI (`report export <runId|batchId> --format allure --out`); another format is `-32602`, and a cursor belongs to the format it was issued for. Every one of them is read through the same service as the CLI, so a caller without the `R` scope (or the `export` permission for code) is refused with the service's `FORBIDDEN`. `resources/list` lists every visible project and run, so project ids are discoverable without a tool. Report and artifact pages carry the real `mimeType`: textual media types (JSON, any `+json`/`+xml`, `text/*`, XML, NDJSON, JavaScript, YAML) are `text` contents and binary ones (images, video, archives) are `blob` (base64). Text pages are cut on UTF-8 character boundaries; `_meta` carries `testmaster:next`, `testmaster:offset` and `testmaster:sizeBytes` in bytes (a report is a JSON document: concatenate the pages, then parse). An unknown or missing resource is JSON-RPC `-32002`; a malformed URI is `-32602`. `/revisions/{id}/plan` of a generated-code revision (no plan) is `-32002` too; its message says the revision is generated code and names `testmaster://revisions/{id}/code` as the way to read it. `tools/call` with an unknown tool name is JSON-RPC `-32602`, not an `isError` tool result. Essas URIs são do servidor MCP, não URLs externas. Prompts opcionais `onboard_project`, `verify_change`, `triage_failure`; versionados, nunca fazem patch do produto autonomamente. Arquivos da app/DOM/reports são conteúdo não confiável, não novas instruções do sistema.

An unknown resource URI is `-32002` and its message names the requested URI (cut at 200 characters), the templates that read the collection it started in (for example `testmaster://tests/{id}/revisions/{revisionId}` points to `testmaster://revisions/{id}` for a revision and `testmaster://tests/{id}/revisions` for the revisions of a test) and `resources/templates/list`.

Long jobs retornam receipt rapidamente; progress/cancellation token usados quando negociados. Desconexão de MCP não significa cancel remoto. Root fora dos roots aprovados ou symlink escape recusado. Secrets não via tool arg livre: aceitar secretRef ou input seguro fora do transcript. Sampling do cliente só quando o cliente anuncia a capability e a política do operador a permite; BYOK gateway é modo separado e explicitado.

Tool metadata: every input property has a description; `budget`, `limits` and `mode` are typed, and `generate_tests` takes `proposalIds` or `revisionIds` (at least one, enforced at run time); no advertised input schema uses a top-level `anyOf`/`oneOf`/`allOf`. Each advertised output schema has its own `$id` (`urn:testmaster:<tool>:output`), so a client can compile all of them in one validator. Argument errors read `Invalid arguments for <tool>` with each issue once, and an enumeration names its allowed values. Annotation classes: reads (`capabilities`, `validate_document`, `get_run`, `get_analysis`, `review_healing`, `get_evidence`, `open_report`, `compare_runs`) are read-only and idempotent; additive tools (`bootstrap`, `analyze_code`, `normalize_requirements`, `explore`, `generate_plan`, `generate_tests`, `propose_healing`, `analyze_run`, `save_test`, `approve_execution`) create records without altering existing ones and are not destructive; `run_tests`, `cancel_run`, `approve_healing`, `reject_healing`, `review_plan`, `edit_plan`, `promote_revision`, `archive_test`, `archive_source`, `save_suite` and `test_auth_login` are destructive. The hints never replace the scope check.

Sources in the planning flow (MCP, CLI `requirement normalize`/`plan generate` and REST alike): `testmaster_normalize_requirements` takes the revisions that should become requirements, and a PRD section (heading, statement, acceptance criteria) normalizes to one requirement, its criteria being the list items under it. An API specification (`source add --role api-spec`) does not have to be normalized: `testmaster_generate_plan` offers the model the operations and response-schema pointers of every active specification source of the project, so a `jsonSchema` assertion can cite it while the requirements stay scoped to the PRD. No tool input selects the specifications; archiving a source (`source archive`, MCP `testmaster_archive_source`) removes it from the offer and from operation coverage.

Normalization is single-flight per project across processes (the MCP server and the CLI share one database): a request for a project that is already being normalized waits for it instead of starting a second paid call, and only the caller's cancellation ends the wait (a model call has no deadline). When the normalization it waited for committed a snapshot for the same source revisions and the same `provider`/`model` on the version the waiter saw, the waiter returns that snapshot (same `version` and `sourceSnapshotId`) without a model call; otherwise it normalizes on the new version, so two normalizations never fail each other. A holder whose process died frees the project when its lease expires. `REVISION_CONFLICT` therefore means that something other than a normalization (a requirement edit, approval or rejection) changed the requirements during the call: its message names the current version, says the new requirements were not stored and points to `testmaster://requirements/{projectId}` (CLI: `requirement list`) before normalizing again.

`mcp serve` over stdio finishes in-flight calls and exits 0 when the client closes stdin. A missing or unreadable token file is `UNAUTHENTICATED` and names the file and `testmaster token issue --token-file <file>`; a root refusal (`FORBIDDEN`) lists `approvedRoots` (or `clientRoots`) in its details and on stderr.

## 7. Jornadas propostas

```bash
# Local deterministic path; the application must already be running.
testmaster init --mode local
testmaster doctor
testmaster test lint --plan testmaster_tests/login.plan.json
testmaster test create --plan testmaster_tests/login.plan.json --output json
testmaster test run "$TEST_ID" --env local --wait --output json
testmaster artifact get "$RUN_ID" --out .testmaster/failure
# Apply application fix outside the runner, then replay the same test revision.
testmaster test rerun "$TEST_ID" --wait --output json
```

IA: `source add` → `discover` → `plan generate` → `plan get` → `plan accept --only` → `test run --mode agent` com política e modelo → `test revision promote` após revisão. CI usa a revisão aprovada e `--mode replay --heal off`, nunca `latest` não pinado para release.
