# Changelog

Release notes for the local single-user profile. Version identifiers are source commits; no npm or
registry package is published. Entries state behavior that tests exercise; see
[`docs/support-matrix.md`](docs/support-matrix.md) for the supported platform matrix and
[`docs/operations/local-operations.md`](docs/operations/local-operations.md) for the upgrade and
rollback procedure. A test (`tools/src/distribution/release-notes.test.ts`) fails when the migration
table below drifts from `packages/persistence/migrations/sqlite/`.

## Unreleased

- MCP tools now carry action-oriented descriptions (what the tool does, when to use it, which tool comes next); `testmaster_get_run` states it returns a summary only and points to evidence and analysis before naming a cause.

### Model calls have no deadline

- A model request runs until the provider answers: the gateway has no deadline (`ModelRequest.deadlineMs` is gone) and the provider transport disables undici's 300 s header and body timeouts. Only a caller cancellation (Ctrl-C, client disconnect, run or job cancel) stops a call; it is `PRECONDITION_FAILED "Model request cancelled"` and names the recorded request as `lastModelCallId`. A model call is never `UPSTREAM_TIMEOUT`.
- No surface accepts a model deadline any more: `budget.deadlineMs` is removed from `testmaster_generate_plan`, `testmaster_generate_tests` (budget keeps `modelCalls`), `testmaster_analyze_run` and `testmaster_propose_healing`, `--deadline-ms` from `run analyze` and `heal propose`, `budget` from `AnalysisInput`, `HealingInput` and the REST proposal-generation body, and the deadline field from the portal's proposal generation.
- Analysis and healing jobs renew their lease while the model call runs (60 s lease, renewed every 15 s), so a long call never loses its job; a second caller waits for the job to settle instead of giving up after the old deadline, and a holder that stopped lets its lease expire.
- The wait for a model answer is not charged to any execution deadline. An agent-mode attempt pauses its attempt clock (`AttemptClock`, shared by the host docker executor and the runner harness) while the host resolves an action, and re-arms the remaining time on the answer; the worker records each wait as `attempt.model_wait` and leaves it out of the run's `executionTimeoutMs`, so a retried attempt keeps its time. `testmaster_explore` `timeMs` bounds browser time only, a multi-feature exploration pauses its whole budget while any model call is pending, and only the caller's cancellation cuts its model call.
- The REST routes that run a model (proposal generation and refinement, `POST /runs/{id}/analysis`, `POST /runs/{id}/healing-proposals`, requirement normalization) and `POST /mcp` turn off the server's 30 s socket idle timeout for their connection; other routes keep it (`ServerOptions.connectionTimeoutMs`).
- The eval runner never kills a model command; its trial wall time only stops commands that do no model work and keeps later commands from starting. The development smoke forwarder relays model calls without a timeout.

### Eleventh Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent an eleventh time (46 of 49 runs passed, including a 9/9 gating suite; a healing drill on a candidate revision that was never promoted paid for a model call and was then refused).

- Healing refuses a failed run of a revision that is not the test's active revision before any model call, job or reservation: `PRECONDITION_FAILED` with `reason: "revision_not_active"`, both revision ids and the CLI and MCP steps (save a corrected revision, replay it, promote it). The `REVISION_CONFLICT` raised when the active revision changes while the model call runs now says so (`reason: "active_revision_changed"`) and carries both revision ids.
- When a failed step differs from the same step of a parent revision that passed in the same environment revision, the rules analysis reports `test_fragility` / `fix_test`: the failure follows the test change, not a product change. It names the parent, how many runs it passed and which step fields changed (never their values). The two stored plans are compared with their defaults filled, so a step that only spells out `required` or `timeoutMs` is unchanged, and descriptions are not compared. Without such a change, the manual-review healing reason mentions the passing parent.
- An explicit per-run step limit (`limits.stepTimeoutMs`, CLI `--step-timeout`) caps every step of that run: a step stops at the lesser of its own timeout and the limit, so the limit shortens steps and never lengthens one. Before, the 30 s that saving a plan writes into each step always won. The project's `execution.stepTimeoutMs` stays the default for steps without a timeout. The cap is frozen with the run, inherited by its healing verification, and shown with the applied limits in the evidence manifest's execution snapshot. The runner image is rebuilt.
- When a recorded locator candidate list was cut (`truncated`), on either the passing or the failing side, the equivalence and readiness checks say that uniqueness cannot be proved, instead of a generic reason, and the healing proposal stays manual. They already refused the proof.
- Requirement normalization tells the model that a requirement describes observable product behavior; statements about how the tests are written, run, configured or given credentials are no longer extracted as requirements.
- The JSON report (`report export --format json`, `testmaster://runs|batches/{id}/report`) writes `coverage`, `executionMetrics`, `selection`, `completeness` and `gate` before `runs`, so the first resource page carries the verdict and the metrics. No field was removed or renamed.
- The `testmaster_run_tests` description says that `revisionId` pins one test's revision and that several pinned revisions run as a `testmaster_save_suite` list.

### Tenth Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a tenth time (8 plan tests and 8 generated Playwright tests passed; a suite holding both revisions of each test reported 16/16 passed but 0/8 requirements verified; a stale-locator drill was healed and verified).

- `verifiedRequirementCoverage` judges each test by the latest run of its current test and environment revision. A run of another revision of the same test in the report, such as a suite that pins the code revision next to the active plan, is stale for that test and no longer hides the current revision's passing run.
- Locator evidence (`browser/steps/<step>-locator-N-<phase>.json`) records only elements a locator or a healing replacement can identify (a role, an accessible name or a recorded attribute) plus every matched element, so anonymous wrappers such as `body` and unnamed `div`s no longer spend the 100-candidate budget and push the page's controls out of the evidence. The walk stops at the first identified element past the budget or after 10,000 elements, and either cut sets `truncated`. Computed style and layout are read only for recorded candidates. The runner image is rebuilt.
- The `manual_review_only` healing advice of `analyze_run` says why identity proof is unavailable: no passing run of the test revision exists in the environment revision, or passing runs exist but no observed candidate matches their control. It also says that a healing proposal can still be requested for a reviewer to decide.
- A healing review lists each unmet condition for automatic application separately: the project does not authorize it, the run's frozen configuration or the project's current configuration does not have `healing.mode "apply"`, or the policy hash changed since the run. Each one says that a reviewer approves the proposal instead.
- The `testmaster_save_test` description states that `plan.requirementRefs` is required (`[]` when the plan maps none), and the `testmaster_save_suite` description states how reports treat runs of other pinned revisions.
- The quickstart documents that the egress proxy removes `X-Forwarded-*`, `Forwarded`, `Via` and `Proxy-*` request headers before they reach the target and records their names in `logs/egress.ndjson`.

### Ninth Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a ninth time (5/5 plan tests passed twice as a suite after one locator fix; 4/5 generated Playwright tests passed first time).

- A browser `hidden` assertion, a `countEquals 0` assertion and a `waitFor` with state `hidden` or `detached` on a target scoped to a container that is not on the page now pass at once: an absent container means an absent target, as in Playwright's chained `toBeHidden()`. Before, the runner waited for the container until the step deadline and failed with `assertion_timeout`. A container that matches several elements still fails as ambiguous, and every other step still waits for its container. The runner image is rebuilt.
- Locator evidence (`browser/steps/<step>-locator-N-<phase>.json`) is recorded when the container is absent, with `cardinality: 0` and the page's candidates, instead of being dropped. The rules analysis states a hidden or counted expectation for `hidden` and `countEquals` steps, and reports a locator step without locator evidence as `evidence_unavailable` (with an evidence gap) instead of a null value with response-shape alternatives.
- `http/<stepId>.json` records `request.credentials`: each credential the first hop sent, by header, with its source and a non-secret reference (the `secretRef` id, the `variableRef`, or the auth profile's cookie and header names), never a value. The field is absent when the request sent no credential, so a negative test with a forged session cookie stored as a secret now proves what it sent.
- A failed Playwright code test records a masked screenshot and a redacted DOM snapshot of its page (`browser/code/<test step>-failure.png` and `.html`, kinds `screenshot` and `dom`), with the masking, redaction, scrub and byte limits of declarative browser steps; the harness builds the paths itself, refuses malformed attachments with a warning, and a capture failure never changes the verdict. Exported projects capture nothing.
- The `testmaster_propose_healing` description states that healing proposes locator-only changes to declarative plans and that `healing_not_indicated` and `code_revision` are `PRECONDITION_FAILED` refusals made before any model call.
- A refused document in text output lists each validation issue under the error as `<path>: <message> (<rule>)`, so `test lint` names what is wrong instead of only `INVALID_ARGUMENT: Invalid ExecutablePlan`.

### Eighth Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent an eighth time (6/6 plan tests and 6/6 generated Playwright tests passed, both suites 12/12 twice; a stale-locator drill was diagnosed, healed and verified).

- The model reading of `analyze_run` receives the text, acceptance criteria and review state of the requirements the failed test maps to, and the prompt has it compare the observation with them before naming a product or test cause; the HTTP evidence it reads also carries the response content type and body size (prompt `analyze-8-requirement-comparison`).
- HTTP assertion steps, including those the browser runner delegates, cite the evidence artifact of the response they judge, whether they pass or fail, so a failed status check points at its response directly. The runner image is rebuilt.
- `invalidCredential` has a cookie form, `{"invalidCredential": {"cookie": "<name>"}}`, valid on `Cookie` only: the HTTP runner and the Playwright and pytest exports send `<name>=testmaster-invalid-<random>`, fresh for every request, so a forged session cookie is a negative test that needs no registered secret. `scheme` and `cookie` never combine, `Cookie` no longer takes the scheme or bare-token form (it never produced a cookie), `http/<stepId>.json` records `request.invalidCredentials` without the value, and the plan-generation prompt teaches the three forms.
- `testmaster_review_healing` and `heal review` show who decided a healing proposal, how, when and why (approved or rejected) instead of `Approval: not available`; a rejection now records its reviewer and time. `testmaster_get_run` returns the run's `testId`, `revisionId`, `environmentRevisionId`, `mode` and `origin`, so a verification run names the candidate revision it ran.
- New MCP tool `testmaster_archive_test`; it, `test archive --reason` and `DELETE /v1/tests/{id}` with a `{reason}` body archive a test with an optional reason (1–2000 characters), stored on the test with the actor and time and kept out of the audit trail.
- `testmaster_open_report` also accepts `batchId` (the batch of a `run_tests` receipt) and returns `testmaster://batches/{id}/report`, one report over every member run with the aggregate metrics, like `report export <batchId>` on the CLI.
- `testmaster_analyze_code` derives Next.js file routes only inside a Next.js project (the nearest `package.json` lists `next`, or a `next.config.*` is present) and never derives routes or endpoints from test, spec or story files or from `e2e/`, `fixtures/`, `__fixtures__/` and `__mocks__/` directories, so a Vite SPA's `src/pages/LoginPage.tsx` and `LoginPage.test.tsx` no longer become `route:GET:/LoginPage` features, nor an e2e fixture server's paths routes. `CODE_DETECTOR_VERSION` is 1.8.0.
- The `run_tests` `idempotencyKey` description states its 16–128 character length.
- Requirement approvals are reset only when the evidence a requirement cites changes: a new revision of a source resets the requirements whose cited chunks it no longer holds (compared by chunk content hash), bumps only their versions, and stales only the proposed batches that cite them. The `source add` receipt (CLI, MCP, REST) lists them in `requirementsReset`. Code analysis, detector, runtime, prompt and requested-model changes no longer reset any approval or version; requirements never cite code. Before, any change of the discovery fingerprint cleared every approval of the project silently.
- `testmaster://projects/{projectId}/features` lists only the current features: those of the newest completed full code analysis plus later diff analyses (features no analysis found, such as exploration-observed ones, stay listed). Features an older analysis found and the current one does not are hidden but never deleted, so requirement, exploration and feature-map references to their ids keep working.
- The `analyze_run` model reading can report, in the optional `requirementAgreement` field (prompt `analyze-9-requirement-agreement`), that a failed assertion agrees with an approved requirement the test maps to. When the rules said `product_bug` from that assertion mismatch and TestMaster verifies the claim (the requirement is mapped and approved, the criterion was supplied), the analysis lowers the cause to `unknown`, makes its first next step a review of the test's expectation against that requirement and criterion, and keeps healing not indicated. The model still can never replace a rules cause with another one; claims about unmapped or unapproved requirements are ignored with a stated reason.

### Seventh Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a seventh time.

- Source JSON Schemas that list `required` names only inside `not`, `anyOf`, `oneOf`, `allOf` or `then` now compile and validate: the source-schema Ajv no longer enables `strictRequired`, which `strict` had turned on. The runner image is rebuilt. A cited schema that cannot be compiled is reported before any run (plan validation `schema_uncompilable`; saving or editing the plan and code generation are refused with the pointer and the compile error), and the rules analysis of a run refused for that reason names a test-side cause instead of `cause_unknown`.
- Plan generation no longer offers the model the predicates only the terminal runner executes (`textNotContains`, `exitCodeIn`, `noLingeringProcesses`, `fileExists`, `fileAbsent`), so such a proposal is refused by the schema instead of after the paid call. A refused proposal reports its plan name, step ids, predicates and the call to regenerate it. The planner prompt asks for registered secrets for user names as well as passwords, and keeps account names out of step ids.
- Browser plans that check an element is absent (`hidden`, `countEquals` 0, `waitFor` hidden or detached) right after a page load, with no positive check of the destination page in between, are refused with `negativeBeforeRender` at the offending step by lint, save, edit, `validate_document`, plan validation and proposal generation, because they passed on a page that had not rendered yet. Stored plans keep running, and the planner prompt orders login checks as submit, URL, positive assertion, then the hidden fields.
- `testmaster_review_requirements`, `requirement approve|update` and `PATCH /projects/{id}/requirements` take an optional `reason` (1–2000 characters), stored with the reviewer and time on each approved or edited requirement, shown as `decision` in the requirement review and at `testmaster://requirements/{projectId}`, and kept out of the audit trail. `requirement approve --reason` loses its old 200-character cap. The `testmaster_review_plan` receipt (and `plan accept`, `POST /proposal-batches/{id}/accept`) lists `acceptedProposals`, one `{proposalId, testId, revisionId}` per accepted proposal.
- `verifiedRequirementCoverage` is derived from recorded facts (the latest replay of the mapped active test passed with its gate, fresh revisions, committed evidence and no diagnostic retry) instead of being fixed at 0. Operation coverage counts an operation restated by several OpenAPI sources once, ignoring path parameter names, and a request with literal ids (`/items/7`) now covers its templated operation (`/items/{id}`) when the cited schema belongs to that operation; parameterized operations could never be covered before.
- `testmaster_save_auth_profile` advertises the typed `config` of every auth kind, so a malformed config is rejected with the failing field paths. Exported code metadata lists the secret names the code reads in `requiredInputs.secrets`, matching the `SECRET_*` variables it documents.
- `testmaster_analyze_code` records React Router client routes (`<Route>` JSX with the composed path, framework `react-router`), so a single-page app's `/login` and `/` appear as routes; `CODE_DETECTOR_VERSION` is 1.7.0. A full code scan no longer has a total-bytes limit that silently dropped the last directories of a large repository (Omnigent lost 467 source files, almost all of `web/src`).

### Sixth Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a sixth time.

- A plan with long step ids or download names no longer fails at publication. Artifact storage keys are relative paths bounded at 4096 characters (PATH_MAX) instead of 200, so a passing run with valid step ids keeps its evidence. Migration 23 widens the matching SQLite and PostgreSQL constraint, and the runner image is rebuilt because it bundles the contracts.
- A run whose evidence could not be published (or that recorded any other execution error after its steps) now reports it: `get_run`/`run get` carry `executionError` and a real `reasonCode` (`insufficient_evidence` instead of `assertions_satisfied`), `get_evidence` names the error instead of only "Run evidence is missing", and `analyze_run` no longer says "No failure observed" for a pass whose gate failed. Batch `counts.passed` no longer includes runs whose gate failed; they count as `inconclusive`.
- Normalization sends each Markdown section (heading, statement and acceptance criteria) to the model whole and asks for one requirement per stated behavior, so a PRD with 9 requirements no longer comes back as 29 (one per acceptance bullet plus a summary).
- Plan generation offers the model the operations and response-schema pointers of the project's active API-spec sources, so requirements normalized from a PRD alone still get `jsonSchema` assertions against the OpenAPI document.
- Requirement coverage in reports counts only requirements still in scope; rejected and superseded requirements no longer appear as uncovered.
- `testmaster --version` prints the CLI build with the schema and runner versions that `capabilities` reports. A new source starts at version 1 (it read 2).
- `testmaster_bootstrap` returns its config as `proposedConfig`, a proposal for `testmaster.config.json` that is never written; `config` is gone. The stored environment stays in `environment`, and one aimed at another origin is never retargeted.
- Evidence of a request step whose id contains a secret value (the user name `root` inside `open_root`) keeps the plan's exact `variableRef` text in `captures[]` and `request.bindings[]` of `http/<stepId>.json`; those fields were rewritten to `[REDACTED]` while `stepId` was already exact.
- `testmaster_review_plan`, `testmaster_promote_revision` and `testmaster_approve_healing`, and their CLI (`plan accept|reject`, `test revision promote`, `heal approve`) and REST counterparts, take an optional `reason` (1–2000 characters). It is stored with the reviewer and time on each decided proposal, on the test and its history entry, and on the healing proposal (`heal review` shows it); it stays out of the audit trail.
- New `disabled` assertion predicate, the inverse of `enabled`: the browser runner polls Playwright's `isDisabled` and records the observation on failure; plan lint and the Playwright and pytest exports support it.
- A healing review whose verification already ran and failed reads `Automation: not_eligible` and no longer prints an approval command that `approve` then refuses with "Healing cannot start another verification"; the MCP and CLI texts point to repairing the test or proposing healing for a new failed run.

### Fifth Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a fifth time (8/8 plan tests and 8/8 generated Playwright tests passed; a probe test with a stale locator was diagnosed, healed and verified).

- MCP `testmaster_approve_healing` executes the verification run itself when no worker is live, like `heal approve` in the CLI and `testmaster_run_tests`: the server runs the ephemeral run in the background and the worker settles the proposal when it finishes. Before, the run stayed queued until someone started `worker start`, and `testmaster_get_run` with `wait` gave up after its timeout.
- `worker start` writes `worker <id> ready: …` to stderr once the worker is registered and claiming (also after the `enrolled` line in server mode), so a supervisor or an agent can wait for it. Before, the local worker printed nothing until it stopped.
- Healing approval (manual or automatic) and rejection record `healing.approved` and `healing.rejected` in the audit trail, with the actor, the proposal id and before/after hashes, in the same transaction as the decision; the rejection reason is never written to the audit row.
- `analyze_run` reports a failed locator step as "one element matching {locator}" with the number of matched elements and the visible candidates of the same role (for example `button "Sign in"`), and cites the locator evidence. Before, it read `Expected: null` / `Observed: null (null value)`. The conclusion and the healing advice are unchanged.
- Healing reviews (REST, MCP and CLI) include `riskBasis`, the steps that set the risk class and why: `text mentions "probe"`, an HTTP method, the operation or a declared risk. The review text reads like `Risk: securityProbe (submit_probe_login: text mentions "probe")`. The classification itself is unchanged.

### Fourth Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a fourth time (13/13 plan tests passed; 2 of 13 generated Playwright tests failed on purpose).

- Generated Playwright code can check a response against the source schema a plan's `jsonSchema` assertion cites. Code generation tells the model which schemas (source revision and pointer) the plan cites; the importer accepts only literal `sourceSchemas.violations('<revision>', '<pointer>', value)` calls for those schemas and freezes the resolved schemas into the revision, and the runner and exported projects validate them with the same source-schema Ajv rules as the HTTP runner (`testmaster-fixtures/schemas.json`, `ajv` and `ajv-formats` pinned). Code that skips a cited schema is sent back for repair, and a cited schema that no longer resolves refuses the revision before the paid call. Before, the model never saw the schema and wrote tests that threw "schema not provided".
- Code runs tell an error thrown by the test itself apart from a failed assertion, in the Playwright reporter and the pytest harness: only an `expect`/`AssertionError` (or `pytest.fail`) fails with `assertion_mismatch`; any other exception ends the test `inconclusive` with `insufficient_evidence`, its class as the error code and its message and location. `analyze_run` quotes that message and location, calls it a defect of the test code (`test_fragility`, fix or regenerate the code) or an environment problem when the message is a connection error. Before, every code failure was `assertion_mismatch` and the diagnosis read `Expected: null Observed: null`, cause unknown.
- A run's recorded effective configuration states the environment it executed against (the pinned environment revision's base URL, network profile, locale, timezone and auth profiles, origin `environmentRevision`) instead of the project file's `init` default. Healing approval no longer refuses because the file's `environment` section or `TESTMASTER_BASE_URL` changed, and run comparability reports an environment difference only as `environment-changed`.
- A stale `testmaster_review_plan` answers with proposal ids, states and versions instead of every plan (it was 29 KB); the other proposal and requirement-snapshot conflicts carry compact digests too. `testmaster_edit_plan` reports the batch version that `review_plan` takes. `generate_tests` candidates name their test, test name, source revision and proposal. Requirements read through MCP carry a derived `status` (pending, approved, rejected, superseded). List resources report how many items a page returned, and the revision code listing carries file text inline up to 64 KiB.

### Third Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent a third time.

- A conflict decision now consistently supersedes the conflict's other requirements: they leave `pendingApprovalIds`, approving one is refused with `requirement_superseded` (naming the conflict and the selected requirement), and `plan generate` without an explicit selection leaves them out. Before, a superseded requirement could still be approved, and planning without a selection then failed on it, so no batch could be generated after any adjudication. Approving a requirement whose conflict is undecided names the conflict (`requirement_conflict_unresolved`, `conflictId`), and the CLI `--selected-requirement` option and the MCP `adjudicate` field say that the other requirements are superseded.
- Evidence bundles reserve `meta.json`, `manifest.json` and `.partial` only at the attempt root. A step whose id is `manifest` wrote `http/manifest.json`, which was refused as a "Reserved artifact path"; that aborted the attempt, discarded every step result and ended an all-passing run inconclusive.
- `analyze_run` reads the runner's `logs/protocol.json`. When the evidence protocol failed, the diagnosis names the error and says the test was not judged and that this is not a product or assertion failure. Healing is not indicated, and the next step is to rerun the unchanged test (a repeat is a TestMaster defect to report). It used to answer "cause unknown", and a model reading cannot turn it into a product cause.
- The sandbox egress proxy no longer answers 403 to plain-HTTP requests that carry `X-Forwarded-*`, `Forwarded`, `Via` or `Proxy-*` headers, such as the target frontend's own `X-Forwarded-Email`. It removes them before forwarding, so none reaches the target, and records only their names as `removedHeaders` on the `allow` decision in `logs/egress.ndjson`. A Host mismatch, a bad `Connection` token and a CONNECT request with such headers are still refused. Before, the proxy's own 403s changed what the application under test rendered, without changing the run's outcome.
- `testmaster_bootstrap` creates a `local` environment for the target origin when the project has none. When an existing environment targets another origin, it reports `environment_targets_target: false` with the exact `testmaster_update_environment` call and does not change the environment. `BootstrapReceipt` gains `environment`, and its next actions name MCP tools (`testmaster_add_source`) instead of the CLI.
- `testmaster_run_tests` treats an absent `mode` as replay, so a batch can be re-read by `jobId` alone.
- An unknown `testmaster://` resource names the requested URI and the template that reads what was meant (a test revision is `testmaster://revisions/{id}`).
- Healing a run that did not fail lists the run's `outcome` and a `nextAction`: an inconclusive or blocked run is fixed with a new revision, a replay of that revision and a promote.
- Plan generation tells the model that negative credential cases use visibly fake literal values, never a secrets entry. With `--type auto`, where a visited page ends up (a redirect to login, `return_to`) is asserted on the final URL in a browser plan, and an HTTP 3xx only when a source says the server answers that way.
- An exported imported or generated Playwright project runs on a plain host with `npm ci && npx playwright install chromium && BASE_URL=... npm test`. It ships `testmaster-fixtures/`, installed as `@playwright/test`, which re-exports the pinned stock package and adds the runner's `secrets`, `profileRequest` and `profilePage` fixtures, so authored tests that use them run unchanged. `secrets.get("NAME")` reads `SECRET_NAME`; the profile session comes from `TESTMASTER_PROFILE_STORAGE_STATE` and `TESTMASTER_PROFILE_HEADERS` and is sent to the `BASE_URL` origin only. `export-metadata.json` lists those variables in `environment`. The runner's staged shim and the export are generated from one module in `@testmaster/domain`, so both have the same fixture semantics and messages. Before, the export pinned stock `@playwright/test`, and any test using a runner fixture failed to load.

### Second Omnigent agent run

Found when an omp agent drove the pipeline on Omnigent again, with no authorization step left.

- Redaction no longer rewrites identifiers of the frozen plan: a step id, and the evidence path, `stepId` field, capture name or handle reference that carries it, stays exact when a secret value such as `root` occurs inside it (`assert_root_url` was recorded as `assert_[REDACTED]_url`, so the plan step had no result and an all-passed run ended inconclusive with a failed gate). Observed values stay scrubbed.
- `headerEquals` / `headerMatches` on a credential header (`Set-Cookie`, `Authorization`, `Cookie`, `X-Api-Key`, `Api-Key`) still evaluate the real value but record only presence, cookie names with redacted values and the verdict; the session cookie used to be the step's observed value, visible in run steps, `compare_runs` and JUnit reports. Credential values the target issues (Set-Cookie values, a returned Authorization or api-key header, 8 characters or more) join the attempt's scrub set, so bodies and other runner evidence redact them too.
- Generated Playwright code uses the environment's auth-profile session per test through the `profileRequest` and `profilePage` fixtures (cookies as storage state, header credentials sent to target origins only, no redirect following with credentials); the stock `request` and `page` stay unauthenticated, and a run without a usable session is blocked as `missing_secret` before the code starts. Code generation maps `auth: "profile"` plan steps to those fixtures and sends back for repair code that does not use them.
- A failure in imported Playwright code is reported once, on the innermost failed step; the enclosing `test.step` and test end failed without repeating the error. Rules analysis treats a code step that expected an HTTP status and got a 4xx like a declarative `statusIn` mismatch (401/403 name the environment's auth profiles), and when no step failed it names the plan steps without a recorded result. `compare_runs` across runners, or a plan run against a code run, reports `step-diff-unavailable` and compares the failing step, the HTTP statuses and the steps that share an id.
- `testmaster_generate_plan` accepts `provider`. With `partialGeneration`, a proposal that breaks the output schema or the plan rules is refused alone and the valid ones are stored, with no extra model call (one invalid step used to fail the whole paid generation). Accepting proposals checks only the requirements each proposal cites: a stale one fails with `proposal_requirements_stale`, naming the proposals, the changed requirement ids and the next action, and editing other requirements no longer blocks the accept. `edit_plan` clears the model's warnings of the edited proposal.
- Requirements can be rejected with a mandatory reason (`testmaster requirement reject <id> --reason`, MCP `testmaster_review_requirements` `reject`, `POST /requirements/{id}/reject`). A rejection is audited as `requirement.rejected`, final (approve and edit refuse it with `requirement_rejected`), is never planned, and keeps the snapshot fingerprint, so approved snapshots and proposal batches stay valid. `requirement approve` takes an optional `--reason`.

### Agent autonomy and the Omnigent agent run

Found when an omp agent drove the whole pipeline on Omnigent; the operator decided that no pipeline step asks the user for authorization.

- Plan acceptance, healing approval and rejection, and production execution approvals no longer require a human principal, an interactive session or a special grant: any enabled principal with write permission (a person, an API token or a service-account agent) decides, and the decision records the acting principal and credential kind. The agent-PR approval (SEC-047), state export, step-up and CAPTCHA/WebAuthn checkpoints keep their human gates.
- SEC-022: a credential's approved targets are the secret's `allowedOrigins`; binding auth profiles to an environment needs no approval and is audited as `environment.auth_binding` (actor, environment, before/after hashes of the profile set).

The agent skill describes the agent-driven pipeline.
- Healing: `propose` refuses a Run whose analysis says healing is not indicated with `PRECONDITION_FAILED`, `reasonCode: healing_not_indicated`, the analysis reason and next step, before any job, reservation or model call; the Run's healing attempt is not spent. A model or rules abstention is a normal result (`HealingAbstention`): the CLI exits 0, MCP answers without `isError`, and asking again returns the settled abstention. `test run --heal propose` reports a refused proposal beside the finished run.
- Code analysis stores snapshot paths of up to 4096 characters, so one long path (over 200) no longer refuses a whole repository.
- Browser runs connect a page WebSocket to the target or an additional origin (`ws` maps to `http`, `wss` to `https`); a WebSocket to any other origin is closed and the run is blocked with `egress_denied` naming the origin. Every WebSocket was denied before.

Code export refuses plans using either.
- Plan generation offers the project's auth profiles and the `body.set` / `auth: "profile"` guidance (a proposal with `auth: "profile"` and no profile is sent back for repair as `auth_profile_not_offered`); browser plans must assert rendered content after their last state-changing action (`browser_postcondition_missing`), which closes the blank-page false green of a URL-plus-absence login check. `jsonSchema` pointers resolve `/components/...` and `/definitions/...` with recursive refs bundled, and plan validation reports `schema_pointer_unresolved` instead of a run-time `unsupported_capability`.
- Playwright code tests read secrets through the `secrets.get("NAME")` fixture declared in `CodeReference.secretRefs`; the importer (validator 1.1.0) refuses undeclared names, any other use of `secrets` and `process.env`, the generation prompt offers allowed secrets by name and origins (never values), and a missing secret blocks the run as `missing_secret` before the child starts. Code failures report Playwright's message with its location and expected/received values, analysis names code steps (`playwright_test`, `playwright_step`, `playwright_run`) with non-null expected/observed, and generated revisions record `generationModelCallId` so their provenance knows the model configuration.
- Model input: the fixed 1 MiB / 100000-token caps (`dataPolicy.maxInputBytes` / `maxInputTokens`) are removed. A prompt is refused locally only above the model's declared `contextTokens` (`PAYLOAD_TOO_LARGE`, `details: {promptBytes, contextTokens}`); models that declare neither output nor context limits reserve a 100000-token budget estimate instead of failing; normalization checks the reconciliation size before the first paid batch. Gateway cache keys no longer include the caps.
- A run whose assertions passed but whose gate failed on unavailable evidence reports `reasonCode: evidence_incomplete` and `unavailableEvidence` (CLI `run get`/`run wait`/`test run --wait`, MCP `testmaster_get_run`, the report), and `exitCodeForRun` never returns 0 for a gate that did not pass.
- Rules analysis diagnoses a required `statusIn` mismatch answered with a 4xx (request content, credentials, path, method, state conflict or rate limit) with healing advice `not_indicated` instead of `cause_unknown`. Flake studies count blocked and inconclusive samples: no failure with at least half of them is `unstable_infrastructure`, and their share is a limitation.
- CLI: OpenAPI 3.2 sources are accepted (validated as 3.1, 3.2 fields lifted, unknown keywords are warnings), and `source add` exits 5 with `INVALID_ARGUMENT` and the diagnostics when a source ends `invalid`. `--dry-run` answers a real `validated` verdict and the operations it would perform (`requirement approve`, `plan generate`), and `worker reconcile --dry-run` is no longer swallowed. `--example` works for commands with required options and prints a complete input. `discover` prints the bounded receipt `testmaster_analyze_code` returns (`--full` for the stored discovery), and partial features carry a reason. `test export`/`test import` list `--format` choices and the `--out` refusal names the rule. `docs/usage/dynamic-auth.md` documents the auth-profile file format.

### Agent pipeline corrections

Found when an omp agent drove the whole MCP pipeline on OmniRoute.

- Healing and analysis evidence: only the values of credential-named environment variables with at least 8 characters are scrubbed, so flags such as `INSPECTOR_MASK_SECRETS=true` or `REQUIRE_API_KEY=false` no longer turn every `true`/`false` of the evidence into `[REDACTED]`. That had made healing evidence invalid JSON (`evidence_invalid` before any model call) and diagnosis text read `"exact":[REDACTED]`. Evidence and the exported config (`config show`, `doctor`) are scrubbed structurally (`scrubEvidenceValue`) instead of re-parsing scrubbed JSON text.
- Healing: a failure before any paid model call (evidence phase, `provider_unavailable`, `evidence_unavailable`, `evidence_too_large`, `semantic_failure`, `evidence_invalid`, or a model refusal raised before anything is sent: `provider_credentials_unavailable`, `model_not_declared`, `model_not_configured`, `model_capability_missing`, `model_not_in_inventory`) no longer consumes the Run's only healing request; the next `propose` reopens the same job (the earlier refusal is kept in `progress.unpaidSettlements`) and evaluates again. A missing API key is reported as `detail: provider_credentials_unavailable` with a next action to fix the provider configuration, not as `cancelled`. A request whose paid call started, or that is `reconciliation_required`, stays final (`no_regeneration`); a leased one answers `already_running`.
- HTTP plans: `request` accepts `redirect: "manual"`, so the runner returns the 3xx response (status, headers, `Location`) and an authentication redirect can be asserted; `http/<stepId>.json` records `redirects` (`{url, status, location}` per followed hop) and `response.url` and keeps the `location` header. Cleanup requests accept the field too. Run analysis no longer calls a failed `statusIn` that expects the redirect the runner followed a `product_bug`: it is `test_fragility` with `fix_test` and a next step to set `redirect: "manual"`.
- HTTP plans: a `text` body is sent verbatim under any explicit Content-Type (for example malformed JSON under `application/json`). New response predicates `headerMatches {header, pattern}` (ECMAScript regex, `u` flag, up to 512 characters, validated with the plan) and `cookieAbsent {name}` (no Set-Cookie of the step, redirect hops included, sets that cookie; a Set-Cookie that deletes it, with `Max-Age` of 0 or less or an `Expires` in the past, does not set it, so a response that clears a session passes; only names are recorded). `Authorization`, `Cookie`, `X-Api-Key` and `Api-Key` accept `{"invalidCredential": {"scheme"?}}`: the runner sends a fresh random `testmaster-invalid-…` token, so negative authentication tests need no secret; a 401 for it is an ordinary mismatch, not `manual_auth_required`. The Playwright and pytest exports support all of this (pytest refuses ECMAScript-only regex syntax).
- `testmaster_validate_document` and `test lint` report a union failure only for the branch the document selects (`kind`, `operation`, `predicate`, `runner`, `type`, `by`, `from`): one extra property is one issue at its path (it was 246), an unknown discriminator value is one issue listing the allowed values, and an enumeration is one `enum` issue (it was `anyOf` plus one `const` per literal).
- `testmaster_generate_tests` advertises a flat input object (the top-level `anyOf` hid `provider`, `model` and `budget` from clients); `proposalIds` or `revisionIds` is enforced when the tool runs. `testmaster_normalize_requirements` accepts `provider`, and its description says progress notifications are sent when the request carries `_meta.progressToken`.
- New resource `testmaster://projects/{projectId}/features{?match,cursor}` lists a project's features with their stable keys (`route:GET:/login`), filterable by substring and paged; `testmaster_explore` `featureIds` come from it, and its feature errors name it.
- `testmaster_get_evidence` resource links carry each artifact's own `mimeType` (`image/png`, `text/html`, `application/x-ndjson`, ...) and its relative path as `name`; every link said `application/json` before, so an agent could not tell text pages from base64 ones without reading them.
- A browser egress denial names the denied origin and resource type and how to allow it (`env update … --additional-origin`, which replaces the list); a forwarding failure for an already authorized origin is no longer reported as an unauthorized origin.
- A run that ends `blocked` (`security_precondition_failed`, `approval_required`, `egress_denied`) exits 15 instead of 9; exit 9 remains for refusals to act (`POLICY_DENIED`) and `doctor` FAIL. In a batch, 15 outranks a plain nonpass (1) and yields to a wait deadline (7). CI scripts that matched exit 9 for blocked runs must accept 15.
- `testmaster run analyze --model` returns `modelStatus` in `data`, prints a `Model reading:` line and warns when the model was not used; a missing provider API key is `unavailable` with `reasonCode: provider_credentials_unavailable` (CLI and MCP). A reading refused before anything was sent (that missing key, or a model that is not declared, configured, capable or in the provider inventory) is not final: the next `run analyze --model` / `testmaster_analyze_run` for the Run evaluates it again, so the reading runs once the configuration is fixed, and the refused reading keeps its status. A reading that abstained after a model call stays stored and is not reissued. A failure with no failed step is localized to the first inconclusive or blocked step, and without one the analysis no longer prints "localized to step unavailable".
- `secret set/rotate --file` drops exactly one trailing `\n` or `\r\n`, so a secret written with `echo` or `openssl rand > file` no longer carries the newline. `test revision create` reports `active: false`, a warning and the exact `test revision promote` command.
- Code analysis skips a file as `binary` only when its bytes are not valid UTF-8 or more than a tenth of them are NUL (UTF-16 text, zero-filled data, images or MPEG transport streams named `.ts`). A literal NUL inside a source string, anywhere in the file, no longer drops it (detector 1.5.0).

### Large web application corrections

- `testmaster_analyze_code` on a large repository: stored symbols are capped (200 per file, 20000 per run) and imports keep only relative specifiers, each truncation declared by a run-wide `symbols_truncated`/`imports_truncated` warning; a file over the size limit is skipped as `oversize` instead of failing the analysis; a state over the storage bound reports `{key, bytes, limitBytes}`. A diff (pinned `base..head` or dirty) reads only the changed files, critical tests and their reverse relative-import closure (prefiltered with `git grep`, `PRECONDITION_FAILED` with `details.step: importer_closure` when that fails) and lists the rest in `impact.excludedFiles`, so the 20000-blob / 64 MiB tree limit no longer refuses big repositories. Untracked files are hashed by streaming, so a dirty tree with a file over 25 MiB keeps the same digest instead of failing.
- Next.js App Router `route.ts` handlers become one `endpoint:METHOD:/path` feature per exported HTTP method (function, const, destructured `export const { GET } = ...`, `export { x as GET }`, re-export) instead of a `route:UNKNOWN` page; `export *` and `pages/api` files warn `route_methods_unresolved` instead of guessing; dynamic segments are stored as `{id}`. Components no longer become feature-map entries (the `component` kind is removed); `CodeSummary.features` lists exported components only.
- `node-http` routes are recorded only in files that import `http`/`https`/`http2` and create a server, never in Next/React app files, client code or test files (`*.test.*`, `*.spec.*`, `__tests__/`, `test/`, `tests/`), and take the method compared in the same condition (`req.method === "GET" && ...`). Besides a bare `path`/`pathname`/`route`, the compared value may be any `.pathname` (`url.pathname`, `new URL(req.url).pathname`) or a `.url` compared with a literal path without a query, in either operand order. `CODE_DETECTOR_VERSION` is 1.3.0.
- Environments accept `additionalOrigins` (`env create/update --additional-origin ORIGIN`, `--clear-additional-origins`, `env revisions`): exact third-party origins that page subrequests may reach. They are not target origins (no secret, auth or cookie binding) and offline profiles ignore them. On a `local-loopback` or `private` profile the egress proxy admits a loopback or private additional origin only at its exact host and port and inside the profile's address ranges; `public` still refuses private answers. An image, font, stylesheet or media GET/HEAD to an unapproved origin is aborted and recorded without failing the run; documents, scripts, fetch/XHR, websockets and every other request stay fatal. Each denial is a runner event `egress.denied` (origin, method, resource type, disposition, count) and a `layer: browser_route` line in `logs/egress.ndjson`, and `testmaster_analyze_run` names the denied origin in its facts and security next step.
- On a `private` profile the egress proxy admits the environment base URL at its exact host and port when it resolves inside the private ranges; loopback, metadata and mixed answers stay refused, and a `public` profile still refuses a private base.
- A run finalized by the worker publishes its final `reasonCode` on `run.completed` (the stored run document is unchanged), so the `egress_denied` alert (OPS-028) and the target-caused telemetry now count executed runs, and the CLI exit code of a single run follows the reason registry: `manual_auth_required`, `missing_secret`, `credential_revoked` and `auth_checkpoint_expired` exit 6 (they exited 9 when blocked, 1 when inconclusive).
- A policy refusal after steps started (`egress_denied`, `security_precondition_failed`, `approval_required`; registry effect `blocked`) reduces the run to `blocked` with that reason instead of `inconclusive`; timeouts and lost workers stay `inconclusive`, and a refusal is never retried.
- `testmaster ops alerts evaluate` runs the alert rules once for the workspace (administrator scope) and prints `{fired, resolved, errors}`; firing alerts exit 0 and a rule that could not be evaluated exits 10 (platform unavailable). The local profile has no alert loop, so this is how local alerts are raised.
- A GitHub webhook whose integration secret cannot be read answers `503 UNAVAILABLE` (`reasonCode: webhook_secret_unavailable`, retryable) instead of `401` "Webhook signature is invalid", and is not counted as an authentication failure; a wrong signature with readable secrets is still `401`. GitHub does not redeliver on its own: the 503 marks the delivery as a server-side failure in GitHub's recent deliveries, from where it can be redelivered once the secret store is back.
- `testmaster_generate_plan` / `plan generate`: semantic refusals (schema pointer without a schema, secret not offered, 200-only HTTP plan, invalid plan, type or integration mismatch) are sent back to the model inside the repair loop; a batch still refused is `INVALID_ARGUMENT` with `details {atomicity: "all_or_nothing", refused: [{index, requirementIds, reasonCode, message}], modelCallId}`, and `partialGeneration: true` / `--partial` stores the valid proposals and lists the refused ones in `testmaster:refusedProposals`.
- `testmaster_generate_tests` accepts `provider` and `model` (refused before any model call when unknown); the code-generation prompt states the importer rules, an importer refusal is repaired, its message names the identifier and line, and a call whose every candidate is refused fails with `reasonCode: generated_code_refused` instead of returning an empty success. String and template keys such as `module['require']` are now refused like identifiers.
- Healing approval checks the verification admission before writing: a refusal leaves the proposal version, status and limitations unchanged, and a frozen-configuration conflict names the changed keys with their frozen and current origins (for example `healing.mode` forced off by `CI=true`) with `reasonCode: execution_configuration_changed` and next actions. A token without the `HealingProposal:approve` grant is refused with `reasonCode: approval_grant_required` and the human approval path.
- `testmaster_get_evidence {failedOnly:true}` on a run that did not pass but has no failed step with evidence (for example a 401 reported as `manual_auth_required`) returns the response step's evidence, else the attempt logs, network and console entries.
- Run analysis states artifact availability once per kind, and locator candidates of a failed step include visible unnamed inputs, selects and textareas.
- Exploration waits for the page to settle before observing, describes form controls (never their values) and whether a password field is present, matches approved mutations by placeholder or role and name, and a first page with nothing to act on ends `inconclusive`/`insufficient_evidence` with a description of the page and no model call; a password field on a feature that is not the login page marks it `unreachable`/`login_required`.

### Terminal runner for CLI and TUI programs ([ADR-025](docs/adr/025-terminal-runner.md))

- New plan type `cli` with runner `terminal` (REQ-057, milestone M5, capability `terminal`, enabled). One program per test runs in the same hardened Docker sandbox in two modes: pipes (`run`: stdout and stderr captured separately, exit code) and a PTY session (`launch`, `sendText`, `sendKeys`, `resize`, `signal`, `waitForText`, `waitForExit`) whose screen is read from a headless terminal emulator (`@xterm/headless` 6.0.0 with the pinned beta `@lydell/node-pty` 1.2.0-beta.15 prebuild). `writeFile` prepares files in the isolated working directory or `HOME`. See [Terminal tests](docs/usage/terminal-tests.md) and `specs/11-contract-details.md` section 3.5.

There is no implicit shell; the sandbox `/tmp` is `noexec`; the program environment is explicit and `HOME`, `TMPDIR`, `PWD`, proxy variables and `TESTMASTER_*` cannot be set.

Outcomes reuse the existing reason codes: `assertion_mismatch`, `assertion_timeout`, `execution_deadline`, and `blocked`/`unsupported_capability` with the errno when the program cannot start.

### Consent removal ([ADR-024](docs/adr/024-consent-removal.md))

- **Breaking.** All consent gates are removed, not disabled. Model calls no longer need a project/provider/data-class consent or an unknown-cost grant: the operator provider allowlist (`allowedModelProviders`), minimisation and redaction, the never-sent data classes, budget reservation and the no-fallback rule remain. The CLI `consent grant|revoke|status` commands and `--allow-unknown-cost`, `GET`/`PUT /v1/projects/{id}/model-consents[/{provider}]` and the onboarding `consents` choices no longer exist. `GET /v1/projects/{id}/model-providers` (and the read-only "Model providers" section of the portal settings page) lists providers, their endpoint origin, models and whether the policy allows them.
- Unknown model cost is budget policy: an unpriced model runs with its cost recorded as `unknown`, except under a monetary project budget, where the call is refused before it is sent with `QUOTA_EXCEEDED` and `reasonCode: "budget_exhausted"`. Token ceilings still apply.
- Integrations: the `consent` input/field and the adapter `requiredScopes` check are gone. Configuration needs the administrator scope and the integration records its creating principal as `createdBy`. Revocation is still terminal and clears secret bindings.
- Restore no longer replays consent revocations; secret, image, approval, retention and deletion tightening is unchanged.
- The generated agent skill and instructions section no longer mention consent (version `1.0.0` is unchanged, so previously installed copies report `outdated`; `agent install --yes` refreshes them, user-owned installed skills are not touched).
- Migration 19 drops the `consents` table, migration 20 moves integration consent grantors to `createdBy` and migration 21 strips the removed `choices.consents` from stored onboarding state. Earlier migrations, changelog entries and results under `validation/results`, `evals/results` and `evals/rounds` are historical and keep their original wording.

### Self-hosting exercise corrections

- Untracked provenance content is hashed in bounded chunks with the same digest format; unchanged files are reused using inode and nanosecond timestamp identity, excluding recently changed files. On the local profile the identities and digests persist across processes in `<dataDir>/provenance-cache/untracked-hashes.json` (0600, versioned, bounded, no content or absolute paths; a damaged file is ignored and rewritten), so a cold CLI process no longer rereads every untracked file; the server profile keeps the in-process cache only.
- Imported pytest items and nested `testmaster.step` calls receive unique paired step indexes and collision-safe IDs. Multiple tests no longer collide on the persisted attempt index. The pinned Python runner image includes the correction.
- `heal propose` accepts explicit `--provider` and `--model`, also exposed by REST and MCP; invalid choices fail before creating a job, and model failures identify the selected configuration. There is no implicit model fallback or relaxation of the one-healing-request-per-Run policy.
- Repeated route exploration reuses the existing Feature transactionally and refreshes its title without duplicate stable-key inserts. Observation and persistence failures are surfaced in the discovery job.
- `suite run` names `--queue`, not the unsupported `--wait`, when no worker is live. Incident creation uses `--affected-version` and validates severity before storage.
- Local backup corruption returns `PRECONDITION_FAILED` with `backup_integrity`; unsupported schema versions return `backup_version_unsupported`. Failed restores remove only their newly created destination.
- Markdown source binding is emitted as a safe code span without HTML-escaped JSON. Long-running CLI failures after a startup receipt now emit a terminal error and nonzero exit instead of being swallowed.
- Generated OpenAPI responses now distinguish paginated and unpaged lists, individual entities, composite reports, empty results, streams, binary artifacts and metrics. Success status codes come from the route catalog without changing served statuses; capability and readiness schemas describe the actual application reports.
- OpenAPI sources with recursive local schemas (such as the generated `packages/contracts/openapi.json`) now import as `ready` instead of `invalid` with `cyclic_reference`. References into recursive targets stay references and every operation carries the definitions it needs under `$defs` (`#/$defs/<pointer>`), so assertion schemas are self-contained and finite; the chunk text keeps the reference as written. Cycles that never reach the instance (`A → B → A`, `allOf` self-reference), dangling or malformed pointers and external references are still refused, and the depth and fan-out expansion limits (`reference_limit`) now name the JSON pointer where they were exceeded.
- The source parser version is now `1.1.0` because stored OpenAPI inventories can carry operation `$defs`; revisions imported earlier keep `1.0.0` and their old shape (re-import to refresh), and the discovery inputs fingerprint changes accordingly.

### Worker liveness under writer contention

- A worker loop now repeats its heartbeat, maintenance, claim and offline-mark operations with capped backoff while the SQLite writer lock is contended (`UNAVAILABLE`, `reasonCode: "writer_contention"`), bounded to 20 s per operation and cut short by the abort signal when nothing is in flight. An attempt's lease heartbeat tolerates up to 15 s of contention before the attempt stops. Contention that outlasts the budget ends `worker start` with the typed retryable error instead of an unhandled one, and in-flight attempts are aborted under their fences.
- `server start` (local) no longer keeps serving HTTP after its worker stops: a worker failure (or a drain) is reported on stderr, the server shuts down, and the command exits with the worker's error. `worker start --mode server` treats any workspace worker failure as fatal for the process (previously only `worker_schema_behind`), so a dead workspace loop is never left unrestarted.
- Run-worker capacity accounting and reconciliation exclude analysis, healing and delivery queues. Their resource identifiers are not Run IDs, so concurrent auxiliary work no longer terminates the server with `NOT_FOUND`; a Run queue entry whose Run is genuinely absent still fails explicitly.
- Notification fan-out updates its delivery rows and cursor in one transaction. SQLite writer contention now surfaces as retryable `UNAVAILABLE (writer_contention)` rather than an opaque `INTERNAL`; controller diagnostics expose only bounded error identifiers, never messages or SQL parameters.
- The API error handler contains failures of the denial audit write: an unauthenticated or forbidden request under writer contention now answers the same enveloped `503 UNAVAILABLE` as an authenticated one, instead of Fastify's bare 500.

### Plan generation against OpenAPI sources

- `jsonSchema` assertions now run: the worker resolves each assertion's `sourceRevisionId` + `pointer` (a JSON pointer such as `/paths/~1items/get/responses/200/content/application~1json/schema`) to the dereferenced schema stored with the source revision and hands it to the runner. Before, every such step ended `blocked` with "Named source schema is absent from snapshot".
- `plan generate` prefixes request paths with the first OpenAPI `servers` path (for example `/v1`) when the cited sources agree on it, because an environment base URL is an origin. Requests that already carry the prefix are left alone.
- `plan generate` offers the workspace's non-revoked secret names and ids (never values) so generated requests can send `{ "secretRef": … }` credentials. Proposals that cite a secret that was not offered, a `jsonSchema` pointer that does not reach a schema in the cited revision, or an HTTP plan whose only assertions are 200 status checks are refused with `INVALID_ARGUMENT` before anything is persisted.
