# Changelog

Release notes for the local single-user profile. Version identifiers are source commits; no npm or
registry package is published. Entries state behavior that tests exercise; see
[`docs/support-matrix.md`](docs/support-matrix.md) for the supported platform matrix and
[`docs/operations/local-operations.md`](docs/operations/local-operations.md) for the upgrade and
rollback procedure. A test (`tools/src/distribution/release-notes.test.ts`) fails when the migration
table below drifts from `packages/persistence/migrations/sqlite/`.

## Unreleased

- The distributed compose files and the MinIO evidence tests now pull MinIO from `ghcr.io/quantmind-br/minio@sha256:a1a8bd4a…`, a public, unmodified linux/amd64 mirror of `minio/minio` RELEASE.2025-09-07T16-13-09Z (same layers and configuration), because Docker Hub no longer serves the original. A fresh host can now start the distributed profile without a saved copy of the image.
- `docs/operations/backups.md` gains a runbook for recovering an S3 backup hidden behind a delete marker (list the versions, remove only the marker versions of the catalog entry and the data objects with the backup credential, then verify), and the disaster-recovery table points at it.
- The server no longer writes an `auth.allowed` audit row for a successful `GET`, `HEAD` or `OPTIONS` request. Authenticated writes and every denial are still audited, as are artifact downloads, links, report exports and MCP tool calls. A read therefore no longer waits on the single database writer to record itself and no longer answers `503` `writer_contention` while a long write holds it; an unauthenticated request still does, because its denial must be recorded. `docs/operations/capacity.md` notes that its recorded read figures included that row.
- The portal no longer shows a Run whose assertions passed but whose gate failed as Passed outside the Run page: the project's and the retention page's Run lists, the batch matrix and the comparison sides show it as degraded "Passed, gate failed", and the batch matrix summary counts it as inconclusive.
- Flake studies count a Run whose assertions passed but whose gate failed (evidence not published, cleanup not proven) as `inconclusive`, never as a pass, as batch counts already did, so it no longer lowers the failure rate.
- `docs/operations/distributed.md` now states what happens to a PostgreSQL migration that runs longer than 10 minutes (it fails with `UNAVAILABLE` `database_timeout` and the migration in progress rolls back) and that Ctrl-C does not interrupt a running migration. The 10-minute deadline stays: the database bridge waits synchronously, so it is the only way a stuck migration ends without killing the process.
- The single-server compose `Caddyfile` now closes idle upstream connections to the server after 30 s, below the server's 65 s keep-alive, as the distributed Caddyfile already did, so Caddy never sends a request on a socket the server is closing (a spurious 502).
- `testmaster config show` and `doctor` no longer list `workerHeartbeatMs` and `workerLeaseMs` under `operationalDefaults`: no code read them, and the worker lease and heartbeat are set where the lease repository claims a job.
- Offline mode (`TESTMASTER_OFFLINE`, `profilePolicy.offline`) now also checks the destination a Run is admitted against: a `testmaster:targetUrl` override, or an environment's stored base URL, outside loopback is refused with `POLICY_DENIED` even when the environment's network profile is `local-loopback`. Before, such an override was admitted and only pinned to 127.0.0.1 by the egress proxy.
- A remote worker (`worker start --mode remote`) now holds `worker.lock` in its data directory for its lifetime; a second process on the same directory is refused with `PRECONDITION_FAILED` `lock_busy`, and the lock of a process that died is reclaimed. Right after enrollment the worker removes every sandbox still labelled with its worker id, its leftover Attempt inputs and the sockets directories of those Attempts, so a worker killed mid-Attempt no longer leaves a `tm-att-*` container behind once it restarts; a sandbox it cannot remove refuses the start with `container_cleanup_failed`.
- A container that cannot be removed now reports Docker's reason: `ContainerCleanupError` carries the daemon's stderr (cut to 500 characters, or the exit code when it is empty) in its message and `detail`, and a remote worker reports that reason to the controller. The orphan reaper no longer stops at the first container it cannot inspect or remove; it removes every expired orphan and `testmaster worker reconcile` lists the others under `reapFailures` with their reason. Sandboxes of a remote worker are labelled `io.testmaster.worker=<workerId>`.
- Capacity and isolation evaluation of the distributed profile (M5-08, OPS-034, NFR-006). `node tools/dist/benchmark/m5-capacity.js --out <file>` boots the distributed compose stack with remote workers on one host and measures it against a loopback fixture (there is no target option): Runs per minute and API operations per second with their n and window, p50 and p90 always, p95 only from n ≥ 100 and p99 only from n ≥ 500 (otherwise `null` with the reason), queue, preparation, execution, collection and orchestration overhead separated from the target's service time, a soak with memory, CPU, database and bucket growth per Run, a controller kill, a MinIO restart and a worker partition under load, each judged on invented results, duplicate executions or firings and lease moves, a backpressure burst past the queue bound, and a hardware manifest. Evidence is read through the S3 API, a Run whose assertions passed with a failed evidence gate is never counted as passed, and `--chaos-cases` and `--keep-stack-on-failure` support forensics. Verdicts are met, not met or not measured. `docs/operations/capacity.md` and the support matrix publish the method, the sizing estimate, the limits (one physical host, no hostile multi-tenant isolation claim) and the measured figures of the committed `validation/results/M5-08-capacity.json` (a complete 2,940 s run: soak, three chaos cases and the backpressure burst met; artifact publication up to 64 MiB, more than one host, non-MinIO S3, browser and terminal runners and hostile multi-tenancy not measured). The host facts moved from `server-load.ts` to `tools/src/benchmark/hardware.ts` without a behaviour change, and `BenchClient` can talk HTTPS with a CA. The owner's browser session (30 min idle, 12 h absolute) is renewed when a setup call finds it lapsed, and a phase that throws still writes the result with the finished phases, the failure and `not measured` verdicts before exiting non-zero.
- Backups and restore on S3 (M5, OPS-026, VAL-045). `backup.destination` may be `{kind: "s3", endpoint, region, bucket, prefix?, forcePathStyle, accessKeyIdFile, secretAccessKeyFile}` for a separate bucket, ideally in COMPLIANCE Object Lock mode. A backup is laid out as `data/<name>/…` plus its manifest `catalog/<name>.json`, which is written last and is what lists the backup, so `backup list`, verification and retention read one small object per backup instead of walking every evidence object. Every object is written with a conditional put, so a crash leaves only unlisted objects, and a name that exists fails the backup with `backup_object_exists`. `backup restore --mode server <name>` takes the backup's name for an S3 destination, verifies manifest and hashes, restores into an empty S3 evidence prefix behind a `tm-restore-pending` marker object and converges on the same hashes when rerun after a crash. Retention on S3 removes the catalog entry first and reports a backup whose Object Lock has not expired as `locked`, still listed and verifiable, instead of failing; leftovers of crashed backups older than 48 hours are swept through a delimiter listing of `data/`. The server refuses to start when its user can read the backup bucket's credential files unless `backup.allowSharedAccess` is set. New fault points cover the S3 write boundaries (`backup.evidence_object`, `restore.marker_written`, `restore.evidence_object`, `restore.marker_cleared`, `retention.remove`, `retention.object_deleted`, and `publish.*` as an optional hook of `publishBundle`); `fault-matrix-s3.docker.test.ts` crashes each against PostgreSQL and MinIO. The S3 loss rehearsal is recorded in `validation/results/m5-s3-loss-rehearsal.json` and no longer deferred; lock expiry, AWS S3 and production-sized restores are not measured. See [`docs/operations/backups.md`](docs/operations/backups.md) and [`docs/operations/disaster-recovery.md`](docs/operations/disaster-recovery.md).
- Evidence bundles are published through an object-store port (`ObjectStore` in `@testmaster/evidence`; the filesystem implementation keeps the existing `runs/<workspace>/<run>/<attempt>/` layout, an S3-compatible implementation is covered against MinIO). Publication claims a `pending/<workspace>/<run>/<attempt>` marker with a conditional put, writes `meta.json` last and clears the marker when the Run's references commit, replacing the in-bundle `.partial` marker and the `.tm-publish` lock; a second publisher of the same Attempt is refused. Orphan sweeps list `pending/` and remove an unreferenced bundle after the grace; staging orphans stay local. A bundle missing from the store reads as missing evidence, and an unreachable S3 endpoint is `UNAVAILABLE` with `storage_unavailable`, which retention treats like a file-system outage (delayed deletion).
- Distributed profile (ADR-035, M5, OPS-001, SEC-030, OPS-037). `server start --mode distributed --config <file>` runs a controller next to others over one PostgreSQL database and one S3-compatible bucket. The configuration names `storage: {kind: "s3", endpoint, region, bucket, prefix?, forcePathStyle, accessKeyIdFile, secretAccessKeyFile, caFile?, capacityBytes, stagingRoot}`, `server.internalOrigin` (how the other controllers reach this one) and optionally `server.expectedControllers`. The mode never degrades: SQLite is refused with `POLICY_DENIED` `distributed_requires_postgres`, filesystem storage with `distributed_requires_shared_storage`, and a missing `--config` fails the same way. An unreachable bucket is `storage_unavailable` in readiness and `doctor`, admission refuses new Runs, and an Attempt whose evidence cannot be published ends non-green; nothing falls back to a local directory. The vault keeps its ciphertext, active key record and write lock in the bucket, so a secret written on one controller is read on another, and a controller that missed a master-key rewrap fails reads of rewrapped secrets and refuses writes with `vault_key_stale`. Credential files must be mode 0600 and owned by the process user.
- Controllers register in `controller_instances` and renew a heartbeat; one older than 30 s is not live. The scheduler, alerts, retention, the lease reconciler and the other loops that must run once run as elected loops under named rows of `controller_leases` (migration 0029 replaces `scheduler_leases`). A lease lasts 30 s, its holder renews it every 10 s, expiry is judged on the database clock so a controller with a wrong clock can neither take a live lease nor keep an expired one, a takeover raises the fence and a released lease is taken at once. A running elected tick stops when its lease is lost, and the scheduler's firing transaction and a remote Attempt's writes check the fence. A killed leader is replaced within one term plus a poll; the `controllers_below_expected` alert fires when fewer controllers than `expectedControllers` are live.
- A worker call for an Attempt that another controller holds is relayed to that controller (`remote_attempts.controller_id`), and a worker's tunnel stream opened on a controller that does not hold the tunnel session is relayed to the relay recorded in `tunnels.relay_id`. The holder authenticates every relayed request itself, so the worker's own proof and the lease fence still decide; a request that carries the hop header `x-testmaster-forwarded` is never relayed again and gains nothing from it. When the holder is gone the worker gets the ordinary `lease_lost` (Attempt calls) or `tunnel_lost` (streams). Every controller's `server.trustedProxies` must include the other controllers' addresses, because a relayed request keeps its `X-Forwarded-Proto`. Revoking a tunnel through any controller closes its streams on the relay that owns them.
- Proof nonces of signed worker and tunnel calls are single-use across the whole deployment (`worker_proof_nonces`), so a proof replayed to another controller is refused and a bad signature or stale proof spends none. Each controller flushes its counters into `controller_metrics` and the SLO report sums the live controllers; cancelling an exploration job reaches the controller that runs it through `discovery_jobs.cancel_requested_at`.
- A remote worker repeats a call that the proxy in front of the controllers answered with 502 or 504, as it already did after a reset connection or a 503, instead of exiting; a controller never answers those statuses itself, so behind a load balancer a restarting controller no longer takes its workers down.
- Fixed: behind the distributed profile's Caddy, a controller stalled under load reset an idle upstream socket the proxy had just reused, and the client got an empty 502. The server keeps idle connections for 65 s instead of 5 s, `Caddyfile.distributed` closes its idle upstream connections after 30 s, and a controller leaves the rotation only after two failed health probes in a row, so one slow probe of a busy controller no longer leaves Caddy without an upstream. A controller that stops relaying a worker's body at the size limit now closes that connection after its refusal, so the unread rest of the upload no longer keeps the connection, and a shutdown waiting for it, open.
- Reference deployment of the distributed profile: `deploy/compose/compose.distributed.yaml` with `Caddyfile.distributed`, `minio-init.sh`, `server.distributed.example.json` and `.env.distributed.example` runs PostgreSQL 17 with TLS, MinIO with TLS and Object Lock (pinned by digest), two controllers and Caddy balancing both; only Caddy publishes a non-loopback port, no service is privileged or on the host network, and every credential is a file. `minio-init.sh` creates an evidence bucket and a backup bucket with a default COMPLIANCE retention (`TESTMASTER_BACKUP_LOCK_DAYS`) and two users limited to one bucket each, so the controllers cannot read or change a backup. `gen-tls.sh` also issues the MinIO certificate. The runbook is `docs/operations/distributed.md`, and `validation/journeys/m5-distributed.docker.test.ts` runs the stack: shared PostgreSQL and S3 evidence, a Run served by the controller that did not claim it, a killed leader's loops moving to the survivor, a tunnel stream crossing controllers, a backup that survives the loss of the evidence bucket and the database, and the refusals.
- Remote workers (ADR-030). `worker start --mode remote --controller <https origin> --enroll-token-file <file>` runs Attempts on another host's Docker daemon without a database credential: it claims, downloads inputs, reports events, secrets, captures, uploads and the result over HTTPS with its `tm_wrk_` credential (`/v1/workers/{id}/claims` and `/v1/workers/{id}/attempts/{attemptId}/…`). A call for an Attempt whose lease the worker no longer holds is refused with `PRECONDITION_FAILED` `lease_lost` and has no effect. The worker stops an Attempt, its sandbox and its egress, when the last lease it saw expires; the API server's new `lease-reconciler` controller expires leases every 5 s, retries a Run that left no uncertain external effect and completes any other with `retry_unsafe_external_effect`, its planned resources `uncertain`. A Run cancelled while a remote worker runs it ends `cancelled`: the worker learns the cancel from its heartbeat, stops the sandbox and keeps reporting the events the runner sends while it stops. `server worker-enrollment --config <file> --name <name> --out <file>` enrolls a shared pool worker that claims for every workspace under the per-workspace fair share; `POST /v1/workers` still enrolls a private one.
- Environments accept `workerSelector` (`environment create|update --worker-label k=v`, `--clear-worker-selector`): their Runs are claimed only by workers, local or remote, whose labels contain every selected pair. Enrollment labels may no longer use the runtime keys `name`, `pid`, `architecture`, `os`, `capacity`, `actions` or `slots`.
- The capability manifest (`testmaster capabilities`, `GET /v1/capabilities`, `testmaster_capabilities`) reports remote workers as the enabled M5 capability `remote-workers`. The capability `distributed`, which names the whole distributed profile, is enabled with the distributed profile below (ADR-035).
- Remote workers prove possession of their own key (ADR-031). On first start `worker start --mode remote` creates an Ed25519 key in `<data-dir>/worker-key.pem` (mode 0600); `POST /v1/workers/enroll` binds it with a `TestMaster-Proof` header next to the `tm_wrk_` token, and every other remote worker call is signed with it (`Authorization: TM-PoP keyId=…, created=…, nonce=…, signature=…`) instead of carrying the token. A proof signed by another key, for another worker or another path, more than 60 s from the server's clock, or presented a second time is refused with `UNAUTHENTICATED`; a token re-enrolled with another key is refused too and audited as `worker.key_mismatch.denied`. A worker enrolled before this change binds its key on its next start; a worker whose key file is lost must be revoked and enrolled again.
- Self-hosted tunnels (ADR-031, M5-02). `testmaster --endpoint <server> tunnel start --target 127.0.0.1:<port>` (or `[::1]:<port>`) exposes one loopback port of a developer's machine to the project's remote workers until the tunnel ends; `tunnel list`, `tunnel status <id>` and `tunnel stop <id>` manage it, and `GET/POST /v1/tunnels` and `GET/DELETE /v1/tunnels/{id}` are the REST surface. The agent opens its session over HTTPS with a one-use open token valid for 60 s, ends each stream's TLS with its own certificate, which workers pin, and connects only to its target, so the relay in the API process forwards ciphertext. A Run is admitted with `tunnelId` only when the tunnel is active, belongs to the test's project and forwards to the environment's base URL, with an approval naming `tunnel:<id>` even outside production; only remote Docker workers claim it, and their egress refuses every other origin with `tunnel_target_mismatch`. Each session carries at most 32 streams (the 33rd is refused with `QUOTA_EXCEEDED`), 10 MiB/s and 512 MiB, sends a heartbeat every 10 s and ends after three missed ones, at its TTL (default 900 s, at most 3600 s) or on revocation, which closes open streams within 5 s; Runs still bound to an ended tunnel end `cancelled` with `tunnel_lost`. Cancelling a Run, or a worker stopping, closes only that Attempt's streams. The capability manifest reports `tunnels` as enabled; see `docs/operations/tunnels.md`.
- Pull request previews through a tunnel (INT-024, J12). A GitHub repository's settings accept `previewTunnelId`, an active tunnel of the bound project (`PATCH /v1/integrations/{id}/github/repositories/{repositoryId}`); a same-repository head is admitted with that tunnel and runs on a remote worker against the developer's loopback app, while a fork never gets it. Without an approval the head is denied with `admission_failed:POLICY_DENIED` and its checks conclude `action_required` and `failure`; the pull request's new `approvalBinding` field lists what `approval create` needs. An approval is consumed by one Run, so each later head needs its own. `SelectionInput` accepts `tunnelId` and passes it to every Run of the selection.
- DAST, access-control and load probes (ADR-033, M5-06). `test probe create` also accepts `{kind: "dast", startPaths, spider, activeScan, policy, failOn, credentials?}`, `{kind: "access", operations, owner, intruder, expect}` and `{kind: "load", stages, maxConcurrency, request, stopConditions, budget}`. Like property probes, every Run needs a bound `securityProbe` approval and runs only in the Docker sandbox.
- A DAST probe runs OWASP ZAP 2.17.0 in the new optional image `testmaster-runner-zap` (`node containers/build.mjs --only testmaster-runner-zap`): it spiders the start paths, optionally runs an active scan with the `default` or `api-minimal` policy, reports steps `dast:spider`, `dast:active-scan` and one per risk, and fails with `dast_alert` when a risk at or above `failOn` has alerts. `dast/alerts.json` and ZAP's `dast/report.json` are sealed with secret values scrubbed. Without the image the `dast` capability is unavailable and the other runners are unaffected; releases ship two or three images.
- An access probe sends each operation as the intruder (anonymous when `intruder` is empty), then as the owner: an intruder answered 2xx fails with `access_granted`, another unexpected status with `unexpected_status`, and a refused owner is `inconclusive` (`owner_refused`). An intruder that holds an owner credential is refused at creation.
- A load probe sends one request open-loop through its stages within `maxConcurrency`, stops early and fails with `stop_condition` when the rolling five-second error rate or p95 crosses its limit, and seals `load/summary.json` with counts, errors, saturated requests, p50/p95/p99, scheduler lag, hardware and per-stage rates. Stage and budget durations are capped at 900 s, and admission refuses a schedule that outlasts the Attempt with `INVALID_ARGUMENT`.
- DAST and load probes are refused in a `production` environment with `POLICY_DENIED` and `reasonCode` `production_load_refused`, approval or not.
- An execution approval now has to name the origin of a Run's target override (`test run --target-url` or `--local`), not only the environment's origins: the refusal's `binding.originSet` includes it, and an approval for the environment alone no longer admits a Run aimed elsewhere.
- The reference shop gains a `/search` page and the `search-reflected-xss` mutant, which echoes the query unescaped, with an independent oracle check.
- Jira and Linear trackers (ADR-034, M5-07). `POST /v1/integrations` accepts the providers `jira` (`baseUrl`, `email`, `apiTokenSecretRef`, `projectKey`) and `linear` (`apiUrl`, `apiKeySecretRef`, `teamId`, `teamKey`); the integration test only reads the configured project or team. Tracker requests go over HTTPS through the notification egress policy, so private and cloud metadata addresses are refused with `POLICY_DENIED` before anything is sent.
- `testmaster issue import <issueKey> --integration <id>` (`POST /v1/integrations/{id}/issues/import`) stores a ticket's title, description and acceptance criteria as a project source: importing an unchanged ticket returns `unchanged: true` with the same revision, a changed ticket adds a revision, and the ticket text is data for the model, never an instruction (INT-030).
- Issue links for failed Runs (INT-031, INT-033). `issue draft <runId> --integration <id>` (`POST /v1/issue-links`) contacts no tracker; `issue preview` returns the exact payload and its hash, and `issue execute --payload-hash <hash> --acknowledge` sends it, so nothing reaches the tracker without a preview, the previewed hash and an acknowledgement. A failure whose cause is not established is filed as "Unconfirmed failure:" with the `testmaster-unconfirmed` label. A failure with the signature of an open issue (project, test revision, environment, failure kind and failing step) drafts a link to that issue instead of a new one. When attaching the Run fails after the issue was created, the link is recorded as `failed` and a retry attaches to the same issue.
- `issue sync` (`POST /v1/projects/{id}/issue-links/sync`, and every 15 minutes in `server start`) records each filed issue's tracker status, a deleted issue (`syncState: deleted`), a moved one (`conflict`) and a rejected credential (`revoked`). A tracker status never changes a Run, its outcome, its gate or its analyses (INT-032). `issue list [--run <id>]` and `GET /v1/issue-links` list the links.
- Project memory (REQ-044). `memory add|edit|approve|forget|list` and `POST /v1/projects/{id}/memory`, `PATCH|DELETE /v1/memory/{id}` keep facts about a project with their source references, validity window and an Approval record. Only approved entries inside their window whose cited source revisions are still current reach the plan, analysis and healing prompts, as data in `untrustedData.projectMemory` and never in the system prompt. Revising or archiving a cited source retires the entry, an edit clears its approval, `forget` erases its text and sources, and text holding a credential or personal data is refused. The `memory` commands no longer answer `CAPABILITY_UNAVAILABLE`.
- Browser matrix (ADR-032, M5-03). Playwright tests run on Chromium, Firefox or WebKit: `test run` and `test rerun` accept the repeatable `--browser`, `--viewport WIDTHxHEIGHT` and `--color-scheme light|dark` flags plus `--reduced-motion reduce|no-preference`, and run one Run per test and cell; `SelectionInput.matrix` and `RunRequest.cell` carry the same axes over REST. A selection whose tests × cells exceed the batch cell limit (500) is refused with `INVALID_ARGUMENT` and `details.reason` `matrix_too_large` before any Run is created. The cell is frozen in the Run's effective configuration, so comparisons, flake identity and reruns keep cells apart, and the runtime identity names the engine and version the cell used. `TESTMASTER_BROWSER` and `browser.name` in the project configuration now accept `firefox` and `webkit`, and `browser.colorScheme` (default `light`) and `browser.reducedMotion` (default `no-preference`) are new configuration fields.
- `visualMatches` assertions (ADR-032). The step's `expectation` is `{predicate: "visualMatches", baseline: <name>, masks?, threshold?}` on an element locator. The runner captures the element, paints the plan's masks, text inputs, `[data-sensitive]` fields and secret text in magenta, and compares it pixel by pixel, with pixelmatch's default colour tolerance and no image library, against the approved baseline of the test, name and rendering cell that admission froze; it writes `visual/<step>-actual.png` and `visual/<step>-diff.png` and fails with `assertion_mismatch` when more than `threshold` (default 0) of the pixels differ. Without an approved baseline the Run ends `blocked` with `visual_baseline_missing` and keeps `visual/<step>-candidate.png`; a baseline approved with other masks ends it `blocked` with `visual_baseline_stale`. A mask that equals a locator another assertion of the plan checks is refused when the plan is validated.
- The reference shop gains the `visual-price-color` mutant (prices render red, every value stays correct) and the `a11y-missing-label` mutant (the password field loses its label), each with an independent oracle check.
- Visual baselines (ADR-032). `testmaster visual baseline create <runId> --step <id> --name <name>` copies the image a completed Run captured at a `visualMatches` step into a draft baseline, `visual baseline approve <id> --expected-version <n>` approves it and `visual baseline list [--test <id>]` lists them; `GET/POST /v1/visual-baselines` and `POST /v1/visual-baselines/{id}/approve` are the REST surface, and all three commands also run against a server with `--endpoint`. Approving needs an explicit `tests:approve` grant on a bearer token (a signed-in human uses the role default), and the approver must differ from the creator (`FORBIDDEN`, `self_approval`), so with a single local principal a second person approves through a server; approving supersedes the earlier approved baseline of the same test, name and rendering cell, which stays listed. A Run never creates or updates a baseline. The `visual-baseline` CLI group that answered `CAPABILITY_UNAVAILABLE` is gone.
- A Run whose plan compares an image with `visualMatches` runs its pages under a fixed clock (`2026-01-01T00:00:00.000Z`), so a page that shows the current time no longer differs from its baseline in every later Run. Timers keep running, and plans without an image comparison keep the real clock (ADR-032, VAL-041).
- `accessibilityViolations` assertions (ADR-032, M5-04). The step's `expectation` is `{predicate: "accessibilityViolations", maximum: <n>, tags?}` on an element locator; the runner scans that element with axe-core 4.14.0, which now ships in the runner image, and fails with `assertion_mismatch` when more than `maximum` serious or critical elements violate a rule of the selected tags (default WCAG 2.0, 2.1 and 2.2 A/AA plus `best-practice`). Each scan writes `a11y/<step>.json` with the violations, the rules needing review and the WCAG 2.2 A/AA criteria no rule judged (`notVerified`); the step's observation, the Markdown report and the HTML report state that the scan is automated (`automated_scan_only`) and how many criteria it left unverified. A scan that cannot run ends `inconclusive` (`oracle_uncertain`).
- Property probes (ADR-033, M5-05). `testmaster test probe create --file <ProbeInput>` (`POST /v1/projects/{id}/probes`) creates a test whose revision is a probe instead of a plan: `{kind: "property", api: "openapi"|"graphql", sourceRevisionId, operations?, stateful, maxExamples?, checks?, credentials?}` names an imported OpenAPI or GraphQL source, and the Python runner image generates requests from it with Schemathesis 4.32.3 under the Run's seed. Each operation is a required step `property:<METHOD> <path>` (GraphQL `property:<field>`), OpenAPI links add `property:stateful`, and a failed step names its check (`not_a_server_error`, `status_code_conformance`, `content_type_conformance`, `response_schema_conformance`, `ignored_auth`). A failure writes `property/<n>-reproduction.json` and `property/<n>-replay.plan.json`, with credentials as secret references only. A missing dependency or an unreadable description ends the Run `blocked` (`property_dependency_missing`, `property_schema_invalid`), never passed. A probe runs only in the Docker sandbox, and every probe Run, in any environment, needs its own bound `securityProbe` approval. The capability manifest reports `api-property` and `graphql-property`.
- `testmaster run reproduce <runId> --artifact property/<n>-replay.plan.json` (`POST /v1/runs/{id}/reproductions`) turns a probe's stored replay plan into an HTTP test and runs it in replay mode with the probe Run's seed and environment, without a model; a retried request reuses the same test.
- The reference shop's `artifacts/openapi-property.json` describes its API with response schemas and OpenAPI links, and the new `fixtures/reference-graphql` app serves a GraphQL catalog with a mutant whose negative `limit` answers a server error.
- Fixed: an approval could never admit a Run whose limits differed from the effective defaults, such as a GitHub pull request Run (`maxAttempts` 1), because the approval was always bound to the defaults and admission ended in `binding_mismatch`. A refusal's `details.binding` now names the Run's `limits`, and `approval create --limits <json>`, `POST /v1/approvals` and `testmaster_approve_execution` accept them; an approval without `limits` stays bound to the defaults. `approval create` and `testmaster_approve_execution` now check their input against the `ApprovalInput` schema.
- `testmaster ops workers pause --reason <text>` and `ops workers resume --reason <text>` (`POST /v1/operations/worker-claims`, administrator scope) stop and restart claims by every worker of the workspace, local and remote, without touching admission or the Attempts already running; `ops status` reports `claims`. ### Suggestions from the Dokploy agent runs

Features and behavior changes the operator approved after seven Dokploy agent runs.

- `testmaster suite run --wait [--timeout S] [--cancel-on-interrupt]` follows a whole list without a worker (the members run in this process when none is live) and prints the `test run --wait` batch shape `{receipt, members, batch, healing}` with the batch exit code. Without a worker and without `--wait`, the refusal names `--wait` and `--queue`.
- Lists gain `memberIntervalMs` (`suite create|update --member-interval-ms`, MCP `testmaster_save_suite`): a minimum time between the starts of consecutive members of a batch, in batch order. It is frozen at admission and enforced at claim by every worker, the in-process CLI and MCP loops and schedules; a member that ended without starting releases the next. It protects a stateful target from bursts, such as a login rate limit.
- A test can declare `runPolicy: "once"` in its plan (not offered to the model). Once its active revision has a fresh passing replay against the environment's active revision, batches, lists, selections and schedules skip it as `already_passed_once`. The skip neither fails the gate nor the exit code, the report counts that passing run for verified requirement coverage, and a new environment or test revision, another destination or a later non-passing replay runs it again. A single-test run of a satisfied test is `PRECONDITION_FAILED` naming the prior run, and a dependency producer cannot be `once`.
- A browser locator can set `nth` (0-based, applied after `container`, `frame` and `pageAlias`) to act on the n-th of identical elements. The runner and exported Playwright and pytest code take that match without an ambiguity failure, and an index past the last match fails as `assertion_timeout`. Count predicates refuse it (`nthCount`), and healing never produces or replaces such a locator.
- A plan can delete data its browser steps created: a `cleanup` entry with `find` runs a GET `lookup` at cleanup time and deletes the one item whose `keyPointer` equals a plan value, through its `handlePointer` (with `ownerProofPointer` required). Zero matches deletes nothing, two or more is a failed cleanup, a missing handle or owner proof and a paged or truncated list (`Link rel=next`, `totalPointer` above the items returned) are inconclusive, and validation refuses a non-GET lookup, bad pointers and keys no earlier step captured. Code export refuses such a plan.
- Planner prompt `plan-9-locator-nth-cleanup-find` explains `nth` and cleanup by lookup.
- Environments gain `ignoredOrigins` (`env create|update --ignored-origin`, `--clear-ignored-origins`, MCP `testmaster_update_environment`): exact origins whose requests are aborted before they leave the sandbox and recorded as `egress.denied` with disposition `ignored` (`origin_ignored` in `logs/egress.ndjson`), for any resource type, without failing the run. They must not overlap the target or `additionalOrigins` and are never admitted to the proxy. The analysis states them as a fact and never suggests allowing them.
- Imported Playwright and pytest browser code now follows SEC-011 like declarative plans: the shim guards the test's page context, an ignored origin is aborted without failing, and any other non-passive request to a foreign origin ends the run `blocked/egress_denied`. - HTTP plans: JSON bodies take `set` entries (`{pointer, value}`, RFC 6901, literal, `variableRef` or `secretRef`); plan validation refuses a `secretRef`/`variableRef` object nested inside a JSON literal (rule `nestedReference`), which used to send the secret's id as the value. `auth: "profile"` sends the environment's auth-profile session (stored cookies matching the URL, or the profile's header credential) to target origins only; a browser-login profile signs in first in an isolated attempt, and a missing session blocks the run before the request. Code export refuses plans using either.
- Plan generation offers the project's auth profiles and the `body.set` / `auth: "profile"` guidance (a proposal with `auth: "profile"` and no profile is sent back for repair as `auth_profile_not_offered`); browser plans must assert rendered content after their last state-changing action (`browser_postcondition_missing`), which closes the blank-page false green of a URL-plus-absence login check. `jsonSchema` pointers resolve `/components/...` and `/definitions/...` with recursive refs bundled, and plan validation reports `schema_pointer_unresolved` instead of a run-time `unsupported_capability`.
- Playwright code tests read secrets through the `secrets.get("NAME")` fixture declared in `CodeReference.secretRefs`; the importer (validator 1.1.0) refuses undeclared names, any other use of `secrets` and `process.env`, the generation prompt offers allowed secrets by name and origins (never values), and a missing secret blocks the run as `missing_secret` before the child starts. Code failures report Playwright's message with its location and expected/received values, analysis names code steps (`playwright_test`, `playwright_step`, `playwright_run`) with non-null expected/observed, and generated revisions record `generationModelCallId` so their provenance knows the model configuration.
- Model input: the fixed 1 MiB / 100000-token caps (`dataPolicy.maxInputBytes` / `maxInputTokens`) are removed. A prompt is refused locally only above the model's declared `contextTokens` (`PAYLOAD_TOO_LARGE`, `details: {promptBytes, contextTokens}`); models that declare neither output nor context limits reserve a 100000-token budget estimate instead of failing; normalization checks the reconciliation size before the first paid batch. Gateway cache keys no longer include the caps.
- A run whose assertions passed but whose gate failed on unavailable evidence reports `reasonCode: evidence_incomplete` and `unavailableEvidence` (CLI `run get`/`run wait`/`test run --wait`, MCP `testmaster_get_run`, the report), and `exitCodeForRun` never returns 0 for a gate that did not pass.
- Rules analysis diagnoses a required `statusIn` mismatch answered with a 4xx (request content, credentials, path, method, state conflict or rate limit) with healing advice `not_indicated` instead of `cause_unknown`. Flake studies count blocked and inconclusive samples: no failure with at least half of them is `unstable_infrastructure`, and their share is a limitation.
- CLI: OpenAPI 3.2 sources are accepted (validated as 3.1, 3.2 fields lifted, unknown keywords are warnings), and `source add` exits 5 with `INVALID_ARGUMENT` and the diagnostics when a source ends `invalid`. `--dry-run` answers a real `validated` verdict and the operations it would perform (`requirement approve`, `plan generate`), and `worker reconcile --dry-run` is no longer swallowed. `--example` works for commands with required options and prints a complete input. `discover` prints the bounded receipt `testmaster_analyze_code` returns (`--full` for the stored discovery), and partial features carry a reason. `test export`/`test import` list `--format` choices and the `--out` refusal names the rule. `docs/usage/dynamic-auth.md` documents the auth-profile file format.

### Agent pipeline corrections

Found when an omp agent drove the whole MCP pipeline on OmniRoute.

- Healing and analysis evidence: only the values of credential-named environment variables with at least 8 characters are scrubbed, so flags such as `INSPECTOR_MASK_SECRETS=true` or `REQUIRE_API_KEY=false` no longer turn every `true`/`false` of the evidence into `[REDACTED]`. That had made healing evidence invalid JSON (`evidence_invalid` before any model call) and diagnosis text read `"exact":[REDACTED]`. Evidence and the exported config (`config show`, `doctor`) are scrubbed structurally (`scrubEvidenceValue`) instead of re-parsing scrubbed JSON text.
- Healing: a failure before any paid model call (evidence phase, `provider_unavailable`, `evidence_unavailable`, `evidence_too_large`, `semantic_failure`, `evidence_invalid`, or a model refusal raised before anything is sent: `provider_credentials_unavailable`, `model_not_declared`, `model_not_configured`, `model_capability_missing`, `model_not_in_inventory`) no longer consumes the Run's only healing request; the next `propose` reopens the same job (the earlier refusal is kept in `progress.unpaidSettlements`) and evaluates again. A missing API key is reported as `detail: provider_credentials_unavailable` with a next action to fix the provider configuration, not as `cancelled`. A request whose paid call started, or that is `reconciliation_required`, stays final (`no_regeneration`); a leased one is waited on by the next `propose`, which returns its outcome.
- HTTP plans: `request` accepts `redirect: "manual"`, so the runner returns the 3xx response (status, headers, `Location`) and an authentication redirect can be asserted; `http/<stepId>.json` records `redirects` (`{url, status, location}` per followed hop) and `response.url` and keeps the `location` header. Cleanup requests accept the field too. Run analysis no longer calls a failed `statusIn` that expects the redirect the runner followed a `product_bug`: it is `test_fragility` with `fix_test` and a next step to set `redirect: "manual"`.
- HTTP plans: a `text` body is sent verbatim under any explicit Content-Type (for example malformed JSON under `application/json`). New response predicates `headerMatches {header, pattern}` (ECMAScript regex, `u` flag, up to 512 characters, validated with the plan) and `cookieAbsent {name}` (no Set-Cookie of the step, redirect hops included, sets that cookie; a Set-Cookie that deletes it, with `Max-Age` of 0 or less or an `Expires` in the past, does not set it, so a response that clears a session passes; only names are recorded). `Authorization`, `Cookie`, `X-Api-Key` and `Api-Key` accept `{"invalidCredential": {"scheme"?}}`: the runner sends a fresh random `testmaster-invalid-…` token, so negative authentication tests need no secret; a 401 for it is an ordinary mismatch, not `manual_auth_required`. The Playwright and pytest exports support all of this (pytest refuses ECMAScript-only regex syntax).
- `testmaster_validate_document` and `test lint` report a union failure only for the branch the document selects (`kind`, `operation`, `predicate`, `runner`, `type`, `by`, `from`): one extra property is one issue at its path (it was 246), an unknown discriminator value is one issue listing the allowed values, and an enumeration is one `enum` issue (it was `anyOf` plus one `const` per literal).
- `testmaster_generate_tests` advertises a flat input object (the top-level `anyOf` hid `provider`, `model` and `budget` from clients); `proposalIds` or `revisionIds` is enforced when the tool runs. `testmaster_normalize_requirements` accepts `provider`, and its description says progress notifications are sent when the request carries `_meta.progressToken`.
- New resource `testmaster://projects/{projectId}/features{?match,cursor}` lists a project's features with their stable keys (`route:GET:/login`), filterable by substring and paged; `testmaster_explore` `featureIds` come from it, and its feature errors name it.
- `testmaster_get_evidence` resource links carry each artifact's own `mimeType` (`image/png`, `text/html`, `application/x-ndjson`, ...) and its relative path as `name`; every link said `application/json` before, so an agent could not tell text pages from base64 ones without reading them.
- A browser egress denial names the denied origin and resource type and how to allow it (`env update … --additional-origin`, which replaces the list); a forwarding failure for an already authorized origin is no longer reported as an unauthorized origin.
- A run that ends `blocked` (`security_precondition_failed`, `approval_required`, `egress_denied`) exits 15 instead of 9; exit 9 remains for refusals to act (`POLICY_DENIED`) and `doctor` FAIL. In a batch, 15 outranks a plain nonpass (1) and yields to a wait deadline (7). CI scripts that matched exit 9 for blocked runs must accept 15.
- `testmaster run analyze --model` returns `modelStatus` in `data`, prints a `Model reading:` line and warns when the model was not used; a missing provider API key is `unavailable` with `reasonCode: provider_credentials_unavailable` (CLI and MCP). A reading refused before anything was sent (that missing key, or a model that is not declared, configured, capable or in the provider inventory) is not final: the next `run analyze --model` / `testmaster_analyze_run` for the Run evaluates it again, so the reading runs once the configuration is fixed, and the refused reading keeps its status. A reading that abstained after a model call stays stored and is not reissued. A failure with no failed step is localized to the first inconclusive or blocked step, and without one the analysis no longer prints "localized to step unavailable".
- `secret set/rotate --file` drops exactly one trailing `\n` or `\r\n`, so a secret written with `echo` or `openssl rand > file` no longer carries the newline. `test revision create` reports `active: false`, a warning and the exact `test revision promote` command.
- Code analysis skips a file as `binary` only when its bytes are not valid UTF-8 or more than a tenth of them are NUL (UTF-16 text, zero-filled data, images or MPEG transport streams named `.ts`). A literal NUL inside a source string, anywhere in the file, no longer drops it (detector 1.5.0).

Code generation has no CLI or REST surface.

### Large web application corrections

- `testmaster_analyze_code` on a large repository: stored symbols are capped (200 per file, 20000 per run) and imports keep only relative specifiers, each truncation declared by a run-wide `symbols_truncated`/`imports_truncated` warning; a file over the size limit is skipped as `oversize` instead of failing the analysis; a state over the storage bound reports `{key, bytes, limitBytes}`. A diff (pinned `base..head` or dirty) reads only the changed files, critical tests and their reverse relative-import closure (prefiltered with `git grep`, `PRECONDITION_FAILED` with `details.step: importer_closure` when that fails) and lists the rest in `impact.excludedFiles`, so the 20000-blob / 64 MiB tree limit no longer refuses big repositories. Untracked files are hashed by streaming, so a dirty tree with a file over 25 MiB keeps the same digest instead of failing.
- Next.js App Router `route.ts` handlers become one `endpoint:METHOD:/path` feature per exported HTTP method (function, const, destructured `export const { GET } = ...`, `export { x as GET }`, re-export) instead of a `route:UNKNOWN` page; `export *` and `pages/api` files warn `route_methods_unresolved` instead of guessing; dynamic segments are stored as `{id}`. Besides a bare `path`/`pathname`/`route`, the compared value may be any `.pathname` (`url.pathname`, `new URL(req.url).pathname`) or a `.url` compared with a literal path without a query, in either operand order. `CODE_DETECTOR_VERSION` is 1.3.0.
- Environments accept `additionalOrigins` (`env create/update --additional-origin ORIGIN`, `--clear-additional-origins`, `env revisions`): exact third-party origins that page subrequests may reach. They are not target origins (no secret, auth or cookie binding) and offline profiles ignore them. On a `local-loopback` or `private` profile the egress proxy admits a loopback or private additional origin only at its exact host and port and inside the profile's address ranges; `public` still refuses private answers. An image, font, stylesheet or media GET/HEAD to an unapproved origin is aborted and recorded without failing the run; documents, scripts, fetch/XHR, websockets and every other request stay fatal. Each denial is a runner event `egress.denied` (origin, method, resource type, disposition, count) and a `layer: browser_route` line in `logs/egress.ndjson`, and `testmaster_analyze_run` names the denied origin in its facts and security next step.
- On a `private` profile the egress proxy admits the environment base URL at its exact host and port when it resolves inside the private ranges; loopback, metadata and mixed answers stay refused, and a `public` profile still refuses a private base.
- A run finalized by the worker publishes its final `reasonCode` on `run.completed` (the stored run document is unchanged), so the `egress_denied` alert (OPS-028) and the target-caused telemetry now count executed runs, and the CLI exit code of a single run follows the reason registry: `manual_auth_required`, `missing_secret`, `credential_revoked` and `auth_checkpoint_expired` exit 6 (they exited 9 when blocked, 1 when inconclusive).
- A policy refusal after steps started (`egress_denied`, `security_precondition_failed`, `approval_required`; registry effect `blocked`) reduces the run to `blocked` with that reason instead of `inconclusive`; timeouts and lost workers stay `inconclusive`, and a refusal is never retried.
- `testmaster ops alerts evaluate` runs the alert rules once for the workspace (administrator scope) and prints `{fired, resolved, errors}`; firing alerts exit 0 and a rule that could not be evaluated exits 10 (platform unavailable). The local profile has no alert loop, so this is how local alerts are raised.
- A GitHub webhook whose integration secret cannot be read answers `503 UNAVAILABLE` (`reasonCode: webhook_secret_unavailable`, retryable) instead of `401` "Webhook signature is invalid", and is not counted as an authentication failure; a wrong signature with readable secrets is still `401`. GitHub does not redeliver on its own: the 503 marks the delivery as a server-side failure in GitHub's recent deliveries, from where it can be redelivered once the secret store is back.
- `testmaster_generate_plan` / `plan generate`: semantic refusals (schema pointer without a schema, secret not offered, 200-only HTTP plan, invalid plan, type or integration mismatch) are sent back to the model inside the repair loop; a batch still refused is `INVALID_ARGUMENT` with `details {atomicity: "all_or_nothing", refused: [{index, requirementIds, reasonCode, message}], modelCallId}`, and `partialGeneration: true` / `--partial` stores the valid proposals and lists the refused ones in `testmaster:refusedProposals`.
- `testmaster_generate_tests` accepts `provider` and `model` (refused before any model call when unknown); the code-generation prompt states the importer rules, an importer refusal is repaired, its message names the identifier and line, and a call whose every candidate is refused fails with `reasonCode: generated_code_refused` instead of returning an empty success. String and template keys such as `module['require']` are now refused like identifiers.
- Healing approval checks the verification admission before writing: a refusal leaves the proposal version, status and limitations unchanged, and a frozen-configuration conflict names the changed keys with their frozen and current origins (for example `healing.mode` forced off by `CI=true`) with `reasonCode: execution_configuration_changed` and next actions. A token without the `HealingProposal:approve` grant is refused with `reasonCode: approval_grant_required` and the human approval path.
- `testmaster_get_evidence {failedOnly:true}` on a run that did not pass but has no failed step with evidence (for example a 401 reported as `manual_auth_required`) returns the response step's evidence, else the attempt logs, network and console entries.
- Run analysis states artifact availability once per kind, and locator candidates of a failed step include visible unnamed inputs, selects and textareas.
- Exploration waits for the page to settle before observing, describes form controls (never their values) and whether a password field is present, matches approved mutations by placeholder or role and name, and a first page with nothing to act on ends `inconclusive`/`insufficient_evidence` with a description of the page and no model call; a password field on a feature that is not the login page marks it `unreachable`/`login_required`.

### Terminal runner for CLI and TUI programs ([ADR-025](docs/adr/025-terminal-runner.md))

- New plan type `cli` with runner `terminal` (REQ-057, milestone M5, capability `terminal`, enabled). One program per test runs in the same hardened Docker sandbox in two modes: pipes (`run`: stdout and stderr captured separately, exit code) and a PTY session (`launch`, `sendText`, `sendKeys`, `resize`, `signal`, `waitForText`, `waitForExit`) whose screen is read from a headless terminal emulator (`@xterm/headless` 6.0.0 with the pinned beta `@lydell/node-pty` 1.2.0-beta.15 prebuild). `writeFile` prepares files in the isolated working directory or `HOME`. See [Terminal tests](docs/usage/terminal-tests.md) and `specs/11-contract-details.md` section 3.5.
- The program is a fixture imported with `artifact import-fixture` (executed directly from the read-only input mount, mode 0555 only when referenced as a program, `argv[0]` is `fixture-<artifactId>`, size limited by the lesser of `bodyBytes` and `artifactBytes`) or an absolute path inside the runner image. There is no implicit shell; the sandbox `/tmp` is `noexec`; the program environment is explicit and `HOME`, `TMPDIR`, `PWD`, proxy variables and `TESTMASTER_*` cannot be set.
- New assertions on `assert`: inputs `{processStepId, stream}`, `{screen}`, `{file}` and `{clipboard: "osc52"}`; predicates `textNotContains`, `exitCodeIn`, `noLingeringProcesses`, `fileExists`, `fileAbsent`. Assertions on live state poll until the step timeout and report the last observation. OSC 52 is recorded as evidence and never forwarded to the host.
- Evidence kinds `terminal.process`, `terminal.stdout`, `terminal.stderr`, `terminal.cast` (asciicast v2, redacted per output burst) and `terminal.screen`. Outcomes reuse the existing reason codes: `assertion_mismatch`, `assertion_timeout`, `execution_deadline`, and `blocked`/`unsupported_capability` with the errno when the program cannot start.
- Termination signals the process group (SIGHUP and SIGTERM, then SIGKILL) and sweeps `/proc`; inside the container every process other than init and the harness counts as left behind (`lingeringProcesses`) and is killed.
- Executor kind `terminal` (1 vCPU, 1 GiB, 256 PIDs, 1 GiB disk) on image `testmaster-runner`, whose pool reuses the browser concurrency default; `capabilities().runners` and readiness list `terminal`. Admission needs an environment with a `baseUrl` (its origin is the only egress), and every non-assertion step is risk `write`. The runner image now contains the emulator and the PTY prebuild (`images.lock.json` refreshed; the seccomp profile is unchanged) and the worker registration label `actions` is `<count>:<hash>`.
- `testmaster test scaffold --type cli` prints a starting plan; `--type` is now `frontend|backend|cli`.
- Refused with `CAPABILITY_UNAVAILABLE`, not emulated: model generation, editing and refinement of terminal plans, healing, agent mode, code export and the `--unsafe-local` executor (`unsafe-local-terminal`). Windows (ConPTY), macOS, the host clipboard and video recording are not supported.
- Migration 22 lets `test_revisions` accept runner kind `terminal` (SQLite table rebuild, PostgreSQL constraint replacement); schema version is 22.

### Consent removal ([ADR-024](docs/adr/024-consent-removal.md))

- **Breaking.** All consent gates are removed, not disabled. Model calls no longer need a project/provider/data-class consent or an unknown-cost grant: the operator provider allowlist (`allowedModelProviders`), minimisation and redaction, the never-sent data classes, budget reservation and the no-fallback rule remain. The CLI `consent grant|revoke|status` commands and `--allow-unknown-cost`, `GET`/`PUT /v1/projects/{id}/model-consents[/{provider}]` and the onboarding `consents` choices no longer exist. `GET /v1/projects/{id}/model-providers` (and the read-only "Model providers" section of the portal settings page) lists providers, their endpoint origin, models and whether the policy allows them.
- Unknown model cost is budget policy: an unpriced model runs with its cost recorded as `unknown`, except under a monetary project budget, where the call is refused before it is sent with `QUOTA_EXCEEDED` and `reasonCode: "budget_exhausted"`. Token ceilings still apply.
- Integrations: the `consent` input/field and the adapter `requiredScopes` check are gone. Configuration needs the administrator scope and the integration records its creating principal as `createdBy`. Revocation is still terminal and clears secret bindings.
- Restore no longer replays consent revocations; secret, image, approval, retention and deletion tightening is unchanged.
- The generated agent skill and instructions section no longer mention consent (version `1.0.0` is unchanged, so previously installed copies report `outdated`; `agent install --yes` refreshes them, user-owned installed skills are not touched).
- Migration 19 drops the `consents` table, migration 20 moves integration consent grantors to `createdBy` and migration 21 strips the removed `choices.consents` from stored onboarding state. Earlier migrations, changelog entries and results under `validation/results`, `evals/results` and `evals/rounds` are historical and keep their original wording.

### Self-hosting exercise corrections

- Untracked provenance content is hashed in bounded chunks with the same digest format; unchanged files are reused using inode and nanosecond timestamp identity, excluding recently changed files. On the local profile the identities and digests persist across processes in `<dataDir>/provenance-cache/untracked-hashes.json` (0600, versioned, bounded, no content or absolute paths; a damaged file is ignored and rewritten), so a cold CLI process no longer rereads every untracked file; the server profile keeps the in-process cache only.
- Imported pytest items and nested `testmaster.step` calls receive unique paired step indexes and collision-safe IDs. Multiple tests no longer collide on the persisted attempt index. The pinned Python runner image includes the correction.
- `heal propose` accepts explicit `--provider` and `--model`, also exposed by REST and MCP; invalid choices fail before creating a job, and model failures identify the selected configuration. There is no implicit model fallback or relaxation of the one-healing-request-per-Run policy.
- Repeated route exploration reuses the existing Feature transactionally and refreshes its title without duplicate stable-key inserts. Observation and persistence failures are surfaced in the discovery job.
- `suite run` names `--queue`, not the unsupported `--wait`, when no worker is live. Incident creation uses `--affected-version` and validates severity before storage.
- Local backup corruption returns `PRECONDITION_FAILED` with `backup_integrity`; unsupported schema versions return `backup_version_unsupported`. Failed restores remove only their newly created destination.
- Markdown source binding is emitted as a safe code span without HTML-escaped JSON. Long-running CLI failures after a startup receipt now emit a terminal error and nonzero exit instead of being swallowed.
- Generated OpenAPI responses now distinguish paginated and unpaged lists, individual entities, composite reports, empty results, streams, binary artifacts and metrics. Success status codes come from the route catalog without changing served statuses; capability and readiness schemas describe the actual application reports.
- OpenAPI sources with recursive local schemas (such as the generated `packages/contracts/openapi.json`) now import as `ready` instead of `invalid` with `cyclic_reference`. References into recursive targets stay references and every operation carries the definitions it needs under `$defs` (`#/$defs/<pointer>`), so assertion schemas are self-contained and finite; the chunk text keeps the reference as written. Cycles that never reach the instance (`A → B → A`, `allOf` self-reference), dangling or malformed pointers and external references are still refused, and the depth and fan-out expansion limits (`reference_limit`) now name the JSON pointer where they were exceeded.
- The source parser version is now `1.1.0` because stored OpenAPI inventories can carry operation `$defs`; revisions imported earlier keep `1.0.0` and their old shape (re-import to refresh), and the discovery inputs fingerprint changes accordingly.

### Worker liveness under writer contention

- A worker loop now repeats its heartbeat, maintenance, claim and offline-mark operations with capped backoff while the SQLite writer lock is contended (`UNAVAILABLE`, `reasonCode: "writer_contention"`), bounded to 20 s per operation and cut short by the abort signal when nothing is in flight. An attempt's lease heartbeat tolerates up to 15 s of contention before the attempt stops. Contention that outlasts the budget ends `worker start` with the typed retryable error instead of an unhandled one, and in-flight attempts are aborted under their fences.
- `server start` (local) no longer keeps serving HTTP after its worker stops: a worker failure (or a drain) is reported on stderr, the server shuts down, and the command exits with the worker's error. `worker start --mode server` treats any workspace worker failure as fatal for the process (previously only `worker_schema_behind`), so a dead workspace loop is never left unrestarted.
- Run-worker capacity accounting and reconciliation exclude analysis, healing and delivery queues. Their resource identifiers are not Run IDs, so concurrent auxiliary work no longer terminates the server with `NOT_FOUND`; a Run queue entry whose Run is genuinely absent still fails explicitly.
- Notification fan-out updates its delivery rows and cursor in one transaction. SQLite writer contention now surfaces as retryable `UNAVAILABLE (writer_contention)` rather than an opaque `INTERNAL`; controller diagnostics expose only bounded error identifiers, never messages or SQL parameters.
- The API error handler contains failures of the denial audit write: an unauthenticated or forbidden request under writer contention now answers the same enveloped `503 UNAVAILABLE` as an authenticated one, instead of Fastify's bare 500.

### Plan generation against OpenAPI sources

- `jsonSchema` assertions now run: the worker resolves each assertion's `sourceRevisionId` + `pointer` (a JSON pointer such as `/paths/~1items/get/responses/200/content/application~1json/schema`) to the dereferenced schema stored with the source revision and hands it to the runner. Before, every such step ended `blocked` with "Named source schema is absent from snapshot".
- `plan generate` prefixes request paths with the first OpenAPI `servers` path (for example `/v1`) when the cited sources agree on it, because an environment base URL is an origin. Requests that already carry the prefix are left alone.
- `plan generate` offers the workspace's non-revoked secret names and ids (never values) so generated requests can send `{ "secretRef": … }` credentials. Proposals that cite a secret that was not offered, a `jsonSchema` pointer that does not reach a schema in the cited revision, or an HTTP plan whose only assertions are 200 status checks are refused with `INVALID_ARGUMENT` before anything is persisted.

### Operations (OPS-038, local single-user profile)

- `testmaster db upgrade` previews (default) or applies (`--apply --backup-out <dir>`) an ordered offline
  upgrade: read-only preflight, drain, backup of the old schema, migrate, readiness. Pending migrations
  are reported as irreversible before anything changes.
- `make install DATA_DIR=<data dir>` (also used for rollback) checks the candidate release against the data
  directory before replacing the installation: a database schema newer than the candidate, a changed
  migration checksum or a revoked pinned image refuses the install without mutation. Without `DATA_DIR`
  the check is skipped and a warning says so.
- `testmaster image revoke <image-id> --reason <text>` records a durable image revocation. Revoked image IDs
  are refused by the image-lock verifier, by `db upgrade`/`make install` and are carried into restored
  data directories.
- `testmaster backup restore <path> --out <dir> --keep-schema` restores without migrating forward, which is
  the restore point required for rolling back to an older release.
